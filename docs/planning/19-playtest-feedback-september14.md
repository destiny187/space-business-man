# 실제 플레이 피드백 20항목과 분할 개발 계획

2026-09-14 **분할 개발 인계**: 사용자 승인 후 요청별 개발을 10개 커밋으로 반영했다. 번호별 결과·실행 확인·조사 한계는 [188 구현 기록](../production/188-playtest-feedback-delivery.md#번호별-최종-인계)이 최신이다. SOS와 최대 시야 회전 지연은 당시 현상을 재현하지 못했으며, 정상 경로 확인과 남은 비용을 구분했다.

아래 요구/코드 열람/개발 묶음은 문서화 당시의 판단 기록이다. ‘미착수·대기’ 표기는 이력으로 보존하며 현재 상태는 위 인계를 따른다.

## 1. 확정한 범위와 후속 정정

- 원래 번호 1~18을 유지하고 추가 제보를 19·20번으로 이어 누락 없이 추적하며, 관련 변경을 묶어 순서대로 개발한다. 현재 요청은 먼저 문서를 정리하고 필요한 질문을 한 뒤 개발하는 순서다.
- **지도만 개선한다. 실제 지형 생성·지질·광맥 배치는 새 원정을 포함해 그대로 유지한다.** 원형 산지 표시는 실제 지형/분포를 읽어 개선하며 표시를 위해 자원을 재배치하지 않는다.
- **B에서는 미해금 건물만 숨기고, 해금됐지만 재료가 부족한 건물은 비용과 함께 표시한다.** 연구 화면에서는 앞으로 해금할 설비를 찾을 수 있어야 한다.
- **단순 발견의 즉시 재료 보상을 제거하고 도감 기록만 우선 유지한다.** 인간 담당자에게 발견 자료를 제출해 보상받는 기능은 이번 개발에서 제외하고 후속 아이디어로 보존한다.
- 스캔 키는 최초 요청의 E 대신 **우주·지상 공통 T**로 정리한다. Q/E 우주선 롤과 F 접근·연결·상호작용은 유지한다. 사용자 키 변경 지원의 후속 정비는 별도다. 기존 설정/입력 기반을 삭제하거나 하드코딩으로 대체하지 않는다.
- SOS 추가 제보: **“그냥 아무것도 안 뜨고 이제 상호작용도 안 돼.”** 대상 이름은 미확인이다. 완료 후 표현 누락과 실제 진행 불능을 구분해 먼저 보고한다. 즉시 수정할 필요는 없다는 요청을 유지한다.
- 시야거리의 기존 ‘매우 멀리’를 ‘보통’처럼 느끼게 개선하고 싶다는 체감 요구는 기록하되, 실측 전에 프리셋 이름만 바꾸거나 거리를 임의로 확정하지 않는다.

## 3. 이번 코드 열람에서 확인한 사실

실제 게임 실행·사용자 저장 재현·성능 측정은 아직 하지 않았다. 아래는 확인한 코드 경로와 그 한계다.

### 3.1 성간 속도와 자동 접근 — 3·5번

- `scripts/domain/crew_navigation.gd`의 성간 이동은 `transit.galaxy_position`을 출발/도착 좌표 사이에서 보간한다. `nav.speed = boost_speed * sin(PI * travel)`는 별도의 지역 출발 연출에 쓰인다. 코드에도 지역 이동은 표시용이고 은하 위치는 transit이 소유한다고 명시돼 있다.
- `scripts/ui/stellar_transit_overlay.gd::_draw_speed()`는 그 `nav.speed`를 그대로 **m/s**로 그린다. 따라서 현재 숫자를 실제 항성계 간 거리/시간의 속도로 읽으면 맞지 않는다. 항로 좌표의 물리 단위가 확정되지 않은 상태에서 광속 배수나 km/s를 임의로 만들어 붙이지 않는다. 성간 구간은 항로 진행/남은 시간 중심으로 바꾸는 안을 제안한다.
- 같은 항성계에서는 실제 위치를 일반 비행으로 이동할 수 있다. 다른 항성계는 일반 비행의 경계 검사에서 위치를 제한하고 속도를 0으로 만들므로 오래 기다려도 넘어갈 수 없다. **연속 성간 수동 비행을 새로 구현하라는 확정 요청은 아니다.**
- 수동 가속 처리 입구는 `nav.mode != "idle"`이면 반환한다. 자동 접근은 별도 경로에서 순항 속도를 상한으로 사용한다. 5번 증상에 대응하는 코드 제한이 존재한다. 행성 접근뿐 아니라 `space_station.gd`의 정거장 접근도 함께 추적할 필요가 있다.

### 3.2 SOS — 4번

- 구조 신호라는 표현은 `freight_salvage.gd`의 유실 화물, mine 정비, `mission_rescue.gd`의 수송선 구조 등 여러 경로에 사용된다. 과거 제작 기록의 E 설명과 현재 우주 입력 F 경로도 구분한다.
- 현재 제보만으로 특정 사건을 확정하지 않는다. 마지막 원장 상태가 완료인데 표현만 없는지, 다음 단계가 생성되지 않았는지, 대상 선택/상호작용 조건이 사라졌는지 조사해야 한다.
- 수송선 구조는 우주 전투 승리 후 지상 사건을 생성하는 코드가 있지만, 이 코드의 존재만으로 사용자가 만난 SOS가 정상 완료됐다고 판단할 수 없다.
- 조사 결과에는 사건 ID/종류, 변경 전후 단계, 후속 대상 또는 지급 여부, 화면/소리, 재현 여부를 남긴다. 사용자에게 이름을 다시 요구하는 것을 조사 착수 조건으로 삼지 않는다.

### 3.3 지도 — 6·15번

- `scripts/ui/planet_map.gd`는 현재 행성의 화면 텍스처 한 장과 `map_key`를 유지한다. 키에는 초점·배율·화면 크기가 포함되고, 변경되면 `planet_map_bake.gd` 작업으로 화면 전체 320×200 지형 이미지를 다시 계산한다. **캐시가 전혀 없는 것은 아니지만, 과거 좌표·배율별 타일을 재사용하는 구조는 아니다.**
- 화면 이미지는 작업 완료 후 교체된다. 현재 코드에서 원형 점진 공개는 확인되지 않았으며, 사용자가 느낀 점진 로딩의 정확한 원인은 실행 재현으로 확인해야 한다.
- `draw_geology()`는 현재 화면 중심에서 가까운 산지를 정렬해 최대 6개만 표시하고, 화면상 라벨 간격에 따라 일부를 생략한다. 산지 외곽은 공통 타원이다. 화면 이동/배율 변경으로 표시 대상이 바뀔 수 있지만, 이것이 실제 광맥 재추첨이라는 뜻은 아니다.
- 새 지도는 고정 월드 좌표·지형 버전·타일·상세 단계로 자료를 식별한다. 이미 생성한 자료는 재사용하고, 화면 이동/휠은 필요한 영역 조회와 표시 배율만 바꾼다. 디스크 캐시와 메모리 상한은 구현 선택으로 정하고 손상 시 원본 지형에서 재생성한다.
- 원형 로딩은 실제 준비된 타일을 중심 거리순으로 공개하는 표현이다. 가짜 진행률이나 지연 연출을 넣지 않고, 준비된 자료는 즉시 표시한다. ‘지형 데이터 수신 중’, ‘지표 정합 중’은 문구 제안이다.
- 산지 아이콘은 고정된 대표 위치에 놓고, 넓은 분포는 기존 지형의 경사/능선/분지와 실제 생성 분포를 읽은 윤곽·음영으로 표현한다. 관측 전 추정과 확인된 광맥을 구분한다. 보기 좋게 만든 가짜 정밀 지질 경계를 실제 정보처럼 제시하지 않는다.
- 실제 테라포밍 화면과 별개인 지역지도 레이어 `환경·복원`을 삭제하고, 연결 설명문도 함께 정리한다.

### 3.4 시야거리·비 — 8·13번

- `data/client_graphics.json`의 5단계는 **1,200 / 2,400 / 4,800 / 7,200 / 10,000**이다. 지상 단위 기준 1.2 / 2.4 / 4.8 / 7.2 / 10 km 설정값이며 실제 식별 거리 실측이 아니다.
- `crew_surface_scene.gd`가 그 거리를 원경 생성에 전달한다. `distant_terrain.gd`는 높이 샘플·512m 타일을 재사용하고 비동기 생성/업로드 후 교체한다. 원경 샘플 간격은 거리별로 16/32/64m이며 가까운 모든 모델을 10km까지 자세히 그린다는 뜻은 아니다.
- 기본 지형 설정은 청크 폭 24m·활성 반경 2청크다. 근접 상세/충돌과 원경 지형은 별도 범위다. 카메라 far는 설정 거리의 1.6배와 기존 far 중 큰 값으로 적용하지만, 가시거리 체감은 안개·지형 가림·개체 LOD와도 관계있다.
- `terrain_streamer.gd`의 관심 범위는 위치 청크로 결정되며 화면 회전만으로 전체 지형을 새로 생성하는 구조는 아니다. `field_visibility.gd`에는 화면 진입 알림·가림 최적화가 있다. 따라서 회전 지연을 단순히 ‘시야 밖을 모두 삭제하기 때문’으로 단정하지 않고 가림 복귀·노드 모션·업로드·GPU 비용을 구분한다.
- 강우의 `weather_strength`는 이미 `surface_atmosphere.gd`의 구름량·구름색·햇빛에 연결되어 있다. **구름 연결이 전혀 없다는 진단은 맞지 않는다.** 기상 상태 변화, 하늘 셰이더의 실제 구름 면적/두께, 갱신 순서와 강우 시작 시점을 렌더에서 확인한다.

### 3.5 소금꽃·생산 거점·연구 — 14·16·17번

- 소금꽃(`salt_bloom`)은 E 스캔 시 발견 기록을 남기고, 현재 데이터상 ‘젖은 결정 관측’과 ‘마른 결정 채취’ 후속 작업을 완료하면 돌 5·결정 2를 지급한다. `exploration_discoveries.gd::scan()`과 `apply()`의 최종 지급은 서로 다른 경로다. 사용자가 스캔만 한 상태라면 도감 기록만 생기는 것이 현행 코드와 맞는다. 이번 변경에서는 단순 발견의 보상용 후속 절차까지 함께 검토한다.
- 생산 거점은 **행성을 떠난 뒤에도 현지 공장·창고를 운영하고, 복원 정산 후에도 시설을 유지하기 위한 이용권/관리 기능**이다. 생산물은 직접 가서 인수·선적·운송한다. `planet_supply.gd`는 호스트가 착륙선 근처에서 이용권을 관리하게 제한하고, 선박은 행정 진입점이다. 배 안에서 제품을 만드는 기능이 아니다. 부재중 생산은 호스트 세션 진행 중 범위이며 게임 종료 중 생산과 구분한다.
- 이용권을 유지한 정산은 현재 대금 비율이 달라지는 별도 선택이다. 초반 필수 행동으로 가르치지 않는다. 명칭을 ‘현지 생산 이용권’으로 풀어 쓰고 실제 필요 시 노출하는 안은 제안이며, 기능 제거/이전은 미확정이다.
- 자동 조립 설비 데이터는 존재한다. 코드상 경로는 **착륙선 연구 → 공동 설비 → 설비 연구 → 자동 조립 설비**다. `crew_stations.gd` → `progression_research_panel.gd` → `facility_research_panel.gd`가 연결되어 있으며, 안내는 중간 ‘설비 연구’ 단계를 생략한다. J는 ‘탐사 기록’이어서 동일한 연구 구매 화면이 아니다.
- 그러므로 ‘연구 데이터가 없다’고 단정할 수 없다. 중첩 탭 노출/크기/선택 상태/진입 문맥을 실제 화면에서 확인해야 한다. `factory` 카드와 건설 목록, 연구 완료의 호스트 결과까지 연결해 고친다.

### 3.6 FINCH 이륙과 항로 후보 — 추가 19·20번

- **1인 플레이도 플레이어 자신이 호스트다.** 호스트 캐릭터가 공동선/행성을 떠나는 것과 호스트 프로세스가 종료되는 것은 다르다. 지상에 다른 호스트 캐릭터를 남겨야 출동할 수 있는 규칙은 아니다.
- `shuttles.gd::context()`는 출동자 한 명의 항법/착륙 문맥을 구성하고 조종사로 지정한다. `shuttle_board`는 그 문맥으로 `launch_if_boarded(local, {1: actor})`를 실행한다. 따라서 FINCH 단독 이륙은 코드에 존재하는 경로이며, 1인 플레이를 금지해 이번 증상을 회피하지 않는다. FINCH의 같은 항성계 이동 제한은 유지한다.
- **의심 경로를 확인했지만 실행 재현은 아직 없다.** `crew_expedition.gd`는 소형선 이륙 전 FINCH 선체 교체를 요청하고 `planet_arrival.gd::begin_launch()`를 호출한다. 그 안에서 카메라를 비운 뒤 `_prepare_descent()`를 호출하는데, 이 함수는 `requested_hull`이 남아 있으면 카메라를 만들기 전에 반환한다. 호출자는 성공 여부를 확인하지 않고 `landing_camera.position`에 접근하며, 상승 단계도 카메라·효과 준비를 가정한다. 실제 교체 시점에 따른 준비 누락/널 접근 여부가 첫 재현 대상이다.
- `ship_home`과 호출된 FINCH 위치, 선체 접지/교체 완료, 남아 있는 공동선 표면 장면, 우주 좌표로 바뀐 캐릭터/카메라, `ascent → escape_loading → escape → exit_handover`의 진행을 함께 확인한다. 땅속 진입·시야 고정·게임 전체 멈춤을 하나의 원인으로 미리 단정하지 않는다.
- 버그 수정 시 선체/카메라 준비를 기다리는 명시적 상태를 사용하고, 이전 지상 화면은 우주 진입이 준비될 때까지 보존하는 안을 우선 검토한다. 임의 시간 지연만 추가하거나 이륙 후 저장을 초기화하는 방식으로 해결하지 않는다.
- 현재 `ui/nearby_stars.gd`는 외부 우주 시점·항법 idle 등의 조건이 맞으면 바로 방향별 항로 후보와 화면 밖 화살표를 표시한다. 빈 공간 응시 시간 조건은 없다. 사용자 표현의 ‘지도상’은 우선 **우주 비행 화면 위의 항로 후보 표식**으로 해석한다. 직접 연 전체 항성계/은하 지도는 즉시 조작할 수 있게 유지하는 안이며, 지도 자체도 가리려는 의도라면 별도 정정한다.

## 5. 세부 구현 제안과 저장 경계

### 안내·스캔

일반 안내의 한 번 기준은 원정·캐릭터·대상 ID 조합을 제안한다. 거리 문턱과 표시 시간은 데이터로 둔다. 위험 경고·새 사건 상태 변화까지 ‘한 번 봤다’는 이유로 차단하지 않는다. 호버는 미조사 대상의 존재·기본 조작과 이미 조사한 기록을 재조회하며, 처음 상세 데이터를 얻는 행위는 T 스캔으로 통일한다. 안내와 결과 패널은 서로 가리지 않게 한다.

현재 키 재지정의 기반(`play_input.json`, `play_input.gd`)은 이미 있다. 이번에는 공통 스캔 액션/표시명/가이드/저장 키 설정의 호환을 연결하고, 사용자가 요청한 키 변경 기능의 전반 정비는 후속으로 둔다. 명시적 사용자 바인딩과 예전 기본값을 구분하는 이행 방안을 구현 전에 정한다.

### 빈 공간 5초 응시 — 추가 20번

사용자 제안의 5초를 기준으로 채택한다. 여기서 ‘빈 공간’은 행성·선박·정거장·화물·사건 등 실제 조작 대상이 없는 방향이다. 배경 별·성운 자체를 타겟으로 취급해 후보가 영원히 안 뜨는 상태를 만들지 않는다. 의도적인 응시를 위해 같은 방향의 좁은 범위 안에서 5초를 누적하는 안을 제안하며 작은 손떨림 허용 각도는 구현 선택이다. 화면을 크게 돌리거나 실제 대상을 조준하면 누적을 초기화한다.

5초 후 현재 시야 방향의 항로 후보를 우선 표시하고, 관련 없는 전 방향 표식을 다시 한꺼번에 펼치지 않는 안을 사용한다. **나타난 후보에 마우스를 옮기는 것은 숨김 조건으로 삼지 않는다.** 후보 선택 중에는 표시를 유지하고, 실제 다른 대상 조준·메뉴 진입·착륙/성간 전환·전투 시에는 정리한다. 숨긴 후보는 클릭/F 입력 판정에서도 제외한다. 전체 지도는 기존 직접 진입을 유지하며, 응시는 항로 선택 UI를 여는 조건이지 자동 출발 명령이 아니다.

1번의 대상별 일회 안내와 이 5초 타이머를 같은 기록으로 합치지 않는다. 타이머는 로컬 일시 상태여서 저장/네트워크 요청을 보내지 않으며, 항로 후보 데이터가 동일한 동안 재검색/전체 지도 생성을 반복하지 않는다. 확인은 5초 전/후, 중간 실제 대상 조준, 후보 선택 유지, 메뉴/전투 진입의 최소 범위로 수행한다.

### 견인

F 연결 시간·상대 정지 허용치는 조정 가능한 값으로 둔다. 연결 후에는 키 유지와 지속 정밀 조준을 요구하지 않는다. 같은 선박의 화물 원장과 기존 인계 대금·단발 지급을 보존한다. 케이블/견인 궤적은 표시이고 호스트가 연결 여부·운반 주체를 소유한다. 수동 해제/다시 연결·점프·착륙 제한·FINCH 회수는 기존 제약을 열람한 뒤 유지/개선안을 명시한다. 착륙 금지를 조용히 삭제하거나 복잡한 로프 물리로 범위를 키우지 않는다.

### 버리기·건물 해체

개인 소유 일반 자원·장비·표본은 버릴 수 있게 하고, 쌓이지 않는 장비는 개체 한 개와 고유 속성을 보존한다. 임무 전용 운반물은 기존 내려놓기/복구와 일치시키며 삭제로 임무를 막지 않는다. 우클릭은 수량 선택을 열고 취소하면 변하지 않는다. 선내/지상과 공동 창고의 권한·드롭 위치를 구분하고 월드 위치에 안전하게 배치한다.

건물 반환량은 자원별 건설 투입량의 50%를 내림하는 안을 제안한다. 개조 부품 포함 여부·기존 저장에 투입 원장이 없는 건물은 구현 시 데이터와 기존 철거 정책을 대조해 명시한다. 시설 내부의 창고/진행 중 생산 투입물은 건설비의 50%와 별도로 보존/회수 처리한다. 기존 엄폐물의 내구도 비례 반환과 이번 절반 반환 지시의 충돌은 새 절반 반환 요구를 기준으로 정리하고 중복 반환을 막는다. 바닥 물건의 지속/상한은 기존 전리품 저장과 합치되 재접속이나 거리 이탈만으로 공유할 물건을 지우지 않는다.

### 발견·튜토리얼

단순 발견 기록 보상과 실제 자원 채취/표본/사건 성과는 구분한다. 이번 보상 제거를 전투·구난 미션·실제 채광의 모든 전리품 삭제로 확대하지 않는다. 기존에 정상 수령한 재료는 회수하지 않고 도감·조사 ID·기존 완료 상태를 보존한다. 후속 담당자 제출 기능을 지금 도감의 빈 보상 버튼으로 예고하지 않는다.

첫 튜토리얼은 현재 상황에서 필요한 행동 하나와 결과를 보여준다. 제안 흐름은 **T로 후보 행성 확인 → 착륙 → 가까운 기초 자원 채집 → I에서 사용처/보관 확인 → B로 가능한 첫 설비 배치 → 테라포밍에서 현장 문제와 설비 효과 확인**이다. 첫 복원 목표에 맞는 시설을 실제 재료로 연결하고, 자동 조립 설비·로봇은 필요해질 때 선택 성장으로 안내한다. 생산 거점 이용권과 자동화를 초반 필수로 강요하지 않는다. 안내를 닫은 횟수나 버튼 클릭 대신 호스트의 실제 성공으로 진행한다. 새 원정 01 시작과 원정/캐릭터별 저장을 유지한다.

## 6. 단일 행동의 갱신 범위

[필수 행동 범위 검사](../technical/01-godot-architecture.md#단일-행동의-변경갱신-범위--필수-검사)를 각 묶음에 적용한다.

| 행동 | 실제로 바꿔야 할 범위 | 피할 불필요한 처리 |
| --- | --- | --- |
| 안내 호버/만료·카메라 회전 | 해당 안내/가시성/표시 상태 | 매 프레임 저장, 모든 대상 스캔 결과 재계산, 지형 전역 생성 |
| 스캔 완료 | 대상 기록·현재 결과 패널·관련 도감 항목 | 모든 종/지도/시설/인벤토리 재생성 |
| FINCH 이륙 | 해당 소형선/탑승자·선체 교체·카메라·표면/우주 전환 상태 | 공동선/다른 현장의 초기화, 미준비 카메라 접근, 저장/화물 유실 |
| 빈 공간 응시 | 로컬 누적 시간·후보 표식 가시성과 입력 판정 | 매 프레임 저장/전송, 전체 은하 조회·생성 |
| 접근 가속·화물 연결 | 해당 선박 입력/항법·화물 ID/상태 | 관계없는 선박/모든 사건 원장의 매 프레임 깊은 복사 |
| 지도 휠·이동 | 표시 변환·누락 타일 조회/생성 | 월드 변경, 광맥 재추첨, 과거 캐시 전부 폐기 |
| 날씨 전환 | 현재 기상 셀과 하늘/강우 표현 | 시설·지형·도감 전체 재생성 |
| 연구 완료 | 해당 해금·비용·건설 카드 가시성 | 닫힌 모든 패널의 카드 재구축 |
| 버리기/철거/회수 | 해당 소유품·시설/예약/재고·드롭 ID와 관련 연결 | 이중 지급, 저장 전 성공 발행, 무관한 모든 행성 갱신 |

저장 원자성·중복 지급 방지·협동 일관성은 유지한다. 필요한 전체 체크포인트 비용이 남으면 숨기지 않고 기록한다.
