## 호스트가 세계 상태를 확정한다

호스트가 플레이어이면서 세계 시뮬레이션·저장의 기준이 되는 구조를 제안한다. **총 플레이어 6명 = 호스트 1명+클라이언트 최대 5명**이다. 로컬 플레이어도 같은 명령 검증을 거치고, 호스트의 UI가 자원·계약을 직접 수정하는 별도 경로를 만들지 않는다.

Godot의 상위 멀티플레이 API는 서버/클라이언트 연결, RPC, 전송 방식·채널을 제공한다. 접속 ID와 장기 캐릭터 ID는 분리해야 하며, 로컬 네트워크 연결만 성공했다고 인터넷 접속도 검증한 것은 아니다. 구현 후보는 해당 기능을 이용하되 버전·접속 경로를 별도 실증한다. [Godot 공식 멀티플레이 문서](https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html), 확인일 2026-09-06.

| 상태·명령 | 확정 주체 | 클라이언트 역할 |
| --- | --- | --- |
| 이동·선체 조종 | 호스트가 허용 입력·점유자·충돌을 검증 | 자신의 입력 예측, 원격 개체 보간·정정 |
| 채집·건설·창고 | 호스트의 자원·예약·소유 장부 | 작업 의도·대상·수량 요청, 승인 결과 표시 |
| 로봇·생태·환경 | 호스트의 단일 시뮬레이션 | 관련 상태·표현 수신; 인원만큼 중복 계산하지 않음 |
| 발견·추첨·연구 | 호스트가 후보·소비·결과를 확정 | 관측·실험 요청과 확정 결과 표시 |
| 표본·화물·정산 | 호스트가 거래·권한·잔량 검증 후 저장 | 미확정/확정 구분, 재전송 시 같은 작업 ID 사용 |
| 개인 캐릭터·반입 장비 | 소유 프로필을 읽고 호스트가 세션 표현 검증 | 본인 프로필만 제공, 원본 소유권 변경 없음 |

메시지는 세션 ID·실제 송신자·순번·명령 ID·예상 대상 버전과 함께 검사한다. 요청에 적힌 소유자나 좌표를 그대로 믿지 않고 권한·거리·장비·재료·실행 빈도를 확인한다. 임의 파일 경로·실행 객체를 전달받아 로드하지 않는다. 이는 일반 동시 작업·잘못된 요청 검증이며 로컬 파일을 조작하는 악성 호스트까지 막는 중앙 인증 경제를 구현했다는 뜻은 아니다.

## 식별자와 합류 동기화

`world_id`는 호스트의 지속 세계, `session_id`는 이번 접속 회차, `player_id/character_id`는 참가자와 캐릭터, `peer_id`는 현재 통신 연결로 분리한다. 같은 캐릭터의 중복 접속을 막고 재접속 시 같은 세계 내 기록에 연결한다. 닉네임만으로 기존 참가자의 자산에 접근하게 하지 않는다. 계정/플랫폼 인증 방식은 서비스 선택 단계에서 결정한다.

합류 흐름은 `자리 예약 → 게임/콘텐츠/생성 버전 검사 → 신원·장비 확인 → 확정 스냅샷 수신 → 이후 변경분 적용 → 준비 응답 → 캐릭터 활성화`다. 초기 스냅샷과 변경분의 기준 순번을 맞추고 전송 중 발생한 채집·굴착·화물 이동을 누락하거나 두 번 적용하지 않는다. 준비 전 접속자도 정원 예약에 포함한다.

지형 원형은 고정된 시드·버전으로 재현할 수 있으나 **시드가 같다는 이유로 플레이 상태까지 같다고 가정하지 않는다.** 굴착·고갈·시설·표본·문명·평가·계약 변경분은 호스트에서 받아야 한다. 정의·원형 해시가 다르면 정해진 호환 절차 또는 명확한 참가 실패를 제공한다. 맵 전체를 입장 때 무조건 내려받지 않고 합류 지점과 필요한 관심 구역부터 전송한다.

## 공동 선체와 지역 스트리밍

선내 캐릭터는 선체 ID·선내 기준 위치·탑승 상태로 표현한다. 움직이는 선체의 세계 좌표와 승무원의 선내 좌표를 함께 무작정 물리 동기화하지 않는다. 선내를 별도 좌표 공간으로 둘지 실제 이동 강체 위를 걷게 할지는 실증 후 선택한다. 두 방식 모두 다른 승무원의 위치·행동과 같은 선박에 탔다는 상태를 일치시킨다.

조종석·작업 단말은 점유 토큰을 사용하고 권한 인계·연결 종료 때 해제한다. 도약·착륙은 고유 전환 ID 아래 목적지·탑승 명단·연료·화물·출발 상태를 확정한다. 이미 적용한 전환 메시지를 다시 받아도 연료 차감·캐릭터 생성·화물 도착을 반복하지 않는다. 느린 참가자는 전환 대기 상태로 유지하고 지표 충돌·상태 준비 전에 낙하하거나 조작하지 않게 한다.

호스트는 **모든 참가자의 관심 지역 합집합**과 운영 중 작업 구역을 처리한다. 호스트 캐릭터가 떠났더라도 게스트가 있는 지하 청크를 해제하면 안 된다. 클라이언트는 자신의 주변 세부 상태와 탐험대 공통 요약을 수신한다. 같은 지역의 작업·자원·생태는 호스트가 한 번 계산하고, 모든 참가자가 떠난 지역만 기존 집계/정지 규칙으로 전환한다.

원거리 움직임은 낮은 빈도로, 중요 거래·생성·삭제·지형 편집·탑승 전환은 누락을 복구할 수 있게 전송한다. 장거리 지형 전송 때문에 조작·조종 갱신이 막히지 않도록 전송 채널·예산을 분리한다. 구체적 틱·대역폭·청크 크기는 측정 전 확정하지 않는다.

## 저장 경계

| 저장 위치 | 저장 내용 | 저장하지 않을 소유 이전 |
| --- | --- | --- |
| 개인 프로필 | 기본 캐릭터·원본 소유 장비 | 세션 입장/퇴장으로 장비를 차감·재지급하지 않음 |
| 호스트 세계 | 은하·행성·선체·공동 장부·연구·협약·거래 | 게스트의 다른 세계·개인 자산 전체를 덮어쓰지 않음 |
| 호스트의 캐릭터별 블록 | 반입 장비 참조·해당 세계 사용 상태·개인 보관·세계 화물·안전 위치 | 다른 참가자의 캐릭터 ID에 소유권을 붙이지 않음 |
| 접속 임시 상태 | 연결 ID·자리 예약·준비·단말 점유·전송 순번 | 장기 소유권의 유일한 증거로 사용하지 않음 |

초기에는 개인 프로필의 장비 목록을 읽기 전용으로 반입하고 세션에서 생긴 변경은 세계 내 상태로 제한한다. `owner_character_id + source_equipment_id`와 세계 내 표현 ID를 연결하되 해당 표현은 자유 처분 가능한 새 아이템이 아니다. 소유자별 표현은 한 개만 활성화하고 재접속 때 중복 생성하지 않는다.

공동 자산은 한 호스트 저장 거래로 확정한다. 중요한 거래는 디스크에 확정된 뒤 영구 완료로 응답하고, 움직임·일반 진행은 정기 체크포인트의 복구 범위를 표시한다. 저장 중 세계를 잠깐 고정하거나 일관된 스냅샷을 얻는 방법은 선택할 수 있지만 개인 메뉴를 열어 호스트 시뮬레이션이 멈추게 해서는 안 된다.

다른 호스트로 새 장비·재화를 영구 반출하는 기능은 초기 제안에서 제외한다. 이후 추가하려면 양쪽 저장의 수령 확인·거래 중복·롤백·오프라인 복구 정책부터 정한다. 로컬 호스트만으로 전 세계 간 자산 복제를 완전히 막을 수 있다고 약속하지 않는다.

### 이탈·장애·복원

게스트 단절 시 기존 입력과 점유를 해제하고, 세계 화물의 마지막 확정 위치·소유/예약을 보존한다. 재접속 유예 만료는 참가 상태를 바꾸며 기본 소유 장비 삭제나 화물 보상 지급을 하지 않는다. 회수 보관분이 다른 승무원에게 이미 인계됐으면 돌아온 캐릭터에게 다시 지급하지 않는다.

호스트 정상 종료는 새 요청 차단→일관된 저장→종료 통지 순서로 처리한다. 비정상 종료는 모든 게스트의 변경 요청을 정지시키고 마지막 정상 호스트 저장으로 재개한다. 클라이언트 캐시를 임의로 세계 원본으로 승격하거나 자동 호스트 이전을 수행하지 않는다. 재실행 뒤 새 세션 ID를 발급해 옛 요청을 거부하고, 저장된 거래 ID로 재시도 결과만 확인한다.

기존 1.2 세이브는 원본을 보존한 별도 변환 결과에서 호스트 세계·기본 소유자·캐릭터 블록으로 매핑한다. 단일 `profile`을 모든 참가자가 공유하는 개인 프로필로 사용하지 않는다. 세부 데이터 버전·마이그레이션은 [저장 설계](02-data-and-save.md)에 연결한다.

## 접속 방식과 실제 검증

로컬 네트워크의 호스트+게스트로 기본 기능을 검증한 뒤, 실제 인터넷의 서로 다른 네트워크에서 최대 인원·합류·재접속을 확인한다. 친구 초대/방 검색·중계 서비스·NAT 대응·계정 인증은 선택이 남아 있다. ENet 직결 후보만 적고 포트 설정 없이 누구나 접속된다고 안내하지 않는다. 구현·배포 단계에서 선택한 서비스의 지원 기기·연결 실패 안내·비용을 확인한다.

| 검증 | 통과 기준 |
| --- | --- |
| 1·2·6인과 초과 접속 | 호스트 포함 정원 일치, 일곱 번째 거부, 동시 마지막 자리 요청에도 초과 없음 |
| 개인 장비 | 서로 다른 ID·등급·특성 유지, 정상 퇴장·추방·양측 강제 종료 후 원본 소유 보존 |
| 공동 승선 | 조종 인계·전환 재전송·느린 로딩·연결 단절에도 한 선체·한 탑승 상태 |
| 동시 작업 | 마지막 자원 채집·같은 위치 건축·동일 표본 사용·동일 정산 요청이 한 번만 성공 |
| 월드 관심 구역 | 6명이 지표·지하의 서로 다른 구역에 있어도 경로·지형·생태·작업 일치 |
| 시간·이탈 | 개인 메뉴 중 타인 진행, 팀 일시정지 공유, 화물 회수 후 재접속 중복 없음 |
| 네트워크 장애 | 지연·손실·순서 역전·중도 합류·호스트 장애 후 확정 상태 복구 |
| 성능·실행 환경 | 호스트 CPU/메모리·각 클라이언트 프레임·송수신량·합류 시간·저장 시간을 분리 측정 |

시험용 네트워크 조건은 왕복 지연 50/150/300ms와 손실 0/1/5%를 후보로 둔다. 이는 보장 사양이 아니며 LAN·인터넷·실제 Mac/Windows 기기에서 검증한 결과를 구분해 기록한다. 같은 컴퓨터의 다중 창이나 기존 1.2 테스트 통과만으로 6인 온라인 협동을 완료 처리하지 않는다.


## E0-C에서 실제로 선택·구현한 구조

- `FrontierCrewSession`: ENet 직결, 호스트 포함 6명. 접속 준비는 8초, 단절 재접속 자리는 30초로 데이터에 둔다. 새 참가자는 재접속 자격을 개인 파일에 저장한 뒤 ACK를 보내고, 호스트가 참가 상태를 저장한 뒤 활성화한다. 닉네임과 연결 ID를 장기 소유 증거로 쓰지 않는다.
- `FrontierPlayerProfile`: 기본 캐릭터와 장비 원본은 `player_profile.json`, 세계별 재접속 자격은 별도 하위 블록이다. 호스트 저장에는 자격 원문 대신 해시를 둔다. 알 수 없는 장비·버전을 거부하며 기존 원본을 덮어쓰지 않는다. 중앙 계정 인증은 구현하지 않았다.
- `FrontierCrewAuthority`: 호스트 자신의 UI도 같은 요청 경로를 사용한다. 개인별 순번·현재 세션 ID·내용 해시·예상 세계 버전을 검사하며 확정 수령 기록 128개를 보존한다. 오래된 수령 기록이 정리돼도 개인별 마지막 확정 순번 아래의 요청을 재실행하지 않는다. 중요한 명령은 저장 성공 후 응답한다.
- 이동은 호스트의 CharacterBody 충돌, 클라이언트는 입력 전달과 위치 보간이다. 입력이 0.35초 이상 갱신되지 않으면 정지한다. 예측/되감기 보정은 아직 없다. 선내는 고정 좌표 공간이고 외부 선체는 같은 호스트 항해 상태로 렌더링한다.
- 전송 채널 0은 참가·명령·응답을 신뢰성 있게 전달하고, 채널 1은 입력, 채널 2는 반복되는 전체 승무원 스냅샷을 순서가 있는 비신뢰 방식으로 전달한다. 스냅샷은 기본 10Hz이며 빠진 상태는 다음 전체 상태로 복구한다. 큰 지형 변경분의 청크 분할·관심 영역 전송을 대신하는 구조는 아니다.
- 공동 원정은 `crew_world.json`에 저장하고 기존 `campaign.json`과 단독 `exploration_world.json`을 변환하거나 덮어쓰지 않는다. 일반 항해 체크포인트는 5초마다 기록한다. 정상 종료·항해 도착·중요 거래는 별도로 즉시 저장한다. 비정상 종료 후 일반 움직임은 마지막 체크포인트까지 복원하며 게스트는 안전한 선내 위치로 재합류한다.
- 조종사는 전원 준비 후 100만 주소 중 목적지로 이동한다. 도약 중 남은 시간·선체 위치를 저장해 재실행 시 이어간다. 접속 종료 시 들고 있던 세계 화물은 회수 위치에 남기며 개인 장비를 새로 지급하지 않는다. 공동 착륙과 행성 사업으로의 전환은 아직 연결하지 않았다.

현재 수치들은 로컬 실증 설정이다. 인터넷·6인 지표·Windows의 성능 보장값으로 사용하지 않는다. [Godot ENet 문서](https://docs.godotengine.org/en/stable/classes/class_enetmultiplayerpeer.html)의 UDP 직결 제약과 [RPC 채널 문서](https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html)를 기준으로 구현했다.

## 공동 지표·생태 연결

[공동 지표 구현 기록](../production/12-shared-surface-and-ecology.md)에 프로토콜 2, 착륙 회차·현재 행성 검증, 모든 참가자 관심 영역 합집합, 호스트 스캔/굴착/생태 판정, 신뢰 채널 압축 기록, 표본 경합·행성별 회수·착륙 상태 재접속을 기록한다. 현재 누적 굴착 배열 전송의 상한과 후속 청크별 증분 전송을 구분한다. 실제 인터넷과 분산된 6개 작업장의 성능 검증은 별도다.

## 산업 로봇 경로와 패킷 상한

산업 로봇의 탐색 경로는 호스트 시뮬레이션/저장에만 보존한다. 클라이언트에는 고유 ID·위치·등급·배터리·화물·작업 상태를 복사하고 경로 배열은 비운다. 큰 경로를 먼저 복제한 뒤 지우는 방식도 피한다. 클라이언트 배열을 변경해도 호스트의 위치·화물·경로가 바뀌지 않는다.

`test_industry_replica_budget.gd`의 합법적인 최대 크기 상태는 굴착 4,096개, 현장 로봇 4대, 격납고 2대, 로봇당 경로 3,500점을 사용한다. 기존 전체 경로 복제는 1,453,046바이트로 수신 측의 524,288바이트 상한을 초과했다. 화면 상태만 보내면 326,168바이트, 압축 후 116,211바이트이며 6개 수신자용 인코딩/복원 26개 검사가 통과했다. [측정 기록](../production/media/expedition-industry/replica-budget.json).

인코더도 압축 전·후 크기를 모두 검사하고 넘으면 빈 결과를 반환한다. 세션은 이를 전송 성공으로 표시하거나 수신 확인 상태를 갱신하지 않는다. 빈 수신 데이터도 압축 해제 전에 거부한다. 이 검사는 코덱·상한 검사이며 해당 수량을 실제 플레이한 결과나 GPU/인터넷 성능 검증이 아니다. 누적 굴착의 청크 증분 전송, 과도하게 누적된 회수 화물, 장거리 분산 플레이와 지연/손실·장시간 CPU/메모리/대역폭은 후속 검증이다.

## 원정선 정비 저장

`vessel_*` 요청은 호스트 소유자·착륙선 근접·세계 revision을 검사하고 원자적 세계 저장에 참여한다. `vessel` 선택 필드가 없던 저장은 기본 선박으로 읽는다. 모듈 규칙 서명을 콘텐츠 핸드셰이크에 추가하고, 클라이언트도 원정선/모듈 ID·등급·슬롯 구조와 통계 범위를 검사한다. 실제 효과 및 지원하지 않는 전체 화물 질량/표본 회로는 [선박 모듈 기록](../production/16-vessel-refits-and-progression.md)을 따른다.

## 별도 대기실과 세계 실행 단계

2026-09-06 변경: `FrontierCrewAuthority.phase`의 `lobby → playing`은 네트워크 세션 상태다. 세계를 열 때마다 대기실에서 시작하며 저장된 항해·착륙 진행은 그대로 둔다. `lobby_ready`는 별도 사전이며 기존 `member.ready`(출항·착륙 준비)를 재사용하지 않는다. 호스트만 `start_game`을 확정하고 모든 연결 게스트의 준비 및 미완료 참가 핸드셰이크를 검사한다. 시작 저장 실패는 대기실을 유지한다.

대기실에서는 게임 명령·이동 입력·물리 항해·산업 계산·지표 전송을 막는다. UI는 선내/행성 장면 대신 독립 대기 화면을 표시한다. 진행 중 입장의 스냅샷은 `playing`을 유지하며 세계 시드를 재생성하지 않는다. 대기 중 이탈한 참가자의 준비 상태는 폐기한다.

새 기본 파일은 `solo_world_v3.json` / `crew_world_v3.json`이다. 추가 새 은하는 고유 파일을 만들고 `world_selection.cfg`가 최근 혼자/공동 세계의 경로만 기억한다. 원래 파일은 보존한다. 이전 세계 버튼은 기존 `solo_world.json` / `crew_world.json`을 원래 생성 설정으로 연다. `galaxy-v2.json`은 기존 매니페스트 검증을 위한 고정 설정이다.

## 2026-09-09 — 주기적 체크포인트의 작업 스레드

5초 주기 저장은 메인 스레드에서 세계 검증과 깊은 복사 후 단일 작업 스레드로 JSON 직렬화·임시 파일 기록·정확한 재읽기/JSON 파싱 검증·백업·원자적 교체를 수행한다. 도메인 검증과 설정 캐시는 작업 스레드에서 접근하지 않는다. 이전 파일의 검증된 바이트 해시가 일치할 때만 `.bak`를 갱신하고 외부 변경/손상 파일은 `.preserved-*`로 보존한다. 읽기와 동기 저장 성공 때 해시를 갱신한다.

진행 중 작업은 하나만 허용한다. 중요한 거래·도착·정상 종료의 동기 저장은 이전 체크포인트 완료 후 최신 상태를 기록하므로 늦은 작업이 확정 거래를 덮어쓰지 않는다. 비동기 실패는 다음 물리 프레임에 세계 진행을 정지하고 알린다. 작업 중 다음 주기가 오면 중복 작업을 쌓지 않고 다음 주기로 넘긴다. 세계 검증/복사, 거래·생산·스캔의 동기 저장과 종료 대기 비용은 남는다. [실제 확인과 한계](../production/83-background-update-and-save.md).
