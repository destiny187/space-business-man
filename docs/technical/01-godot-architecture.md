## 기존 1.2 기반의 구현 전제

아래 유한 구역·단일 활성 행성·원격 조종 구조는 기존 기반이다. 확장의 단일 은하·자유 탐사·지하·사례 생태를 완료한 구조가 아니다. 새 책임 경계는 마지막 절, 구체적 월드 실증은 [천체 데이터·스트리밍](03-universe-data-and-world-streaming.md)을 따른다.

- 싱글플레이, 한 번에 한 행성을 활성화하는 로컬 게임으로 시작한다.
- 3D 구역과 자원 노드 방식으로 채집·건축·자동화 루프를 먼저 검증한다.
- 기본 구현 언어는 타입을 명시한 GDScript를 제안한다. 특별한 요구가 생기기 전에는 언어·런타임을 혼합하지 않는다.
- 로봇의 AI는 게임 내 작업 선택·상태 전이·경로 탐색이다. 기본 자동화 동작에 외부 생성형 AI 호출은 필요하지 않다.
- 콘텐츠 정의는 Godot Resource 등 데이터 자산, 진행 상태는 고유 ID를 가진 런타임·세이브 데이터로 분리한다.
- 시점·입력·월드 모양은 교체 가능한 경계로 두되 미정 기능을 위한 복잡한 프레임워크부터 만들지 않는다.

## 제안 폴더

아래는 초기 목표 구조다. 현재는 `scenes/app/main.tscn`, `scripts/app`, `domain`, `simulation`, `actors`, `persistence`, `ui`로 구현했으며 정의 데이터는 `data/catalog.json`으로 통합했다. 아래 제안의 모든 하위 폴더가 필요한 것은 아니다.

```text
우주-비즈니스/
  project.godot
  scenes/
    app/                  # 시작·전환·메인 진입
    earth/                # 상점·행성 선택·출발 편성
    planet/               # 환경·지형·자원·기지
    player/               # 원격 수동장비·카메라
    robots/               # 로봇 표현·애니메이션
    buildings/            # 시설 표현·상호작용
    ui/                   # HUD·관리·평가·정산
  scripts/
    app/
    domain/               # 인벤토리·제작·환경·평가·거래 규칙
    simulation/           # 작업·전력·시간 진행
    actors/               # 플레이어·로봇·시설 제어
    persistence/          # 저장·복원·마이그레이션
  data/
    resources/
    recipes/
    robots/
    traits/
    buildings/
    technologies/
    planets/
    events/
    audio/
  assets/
    models/
    textures/
    materials/
    audio/
  tests/                  # 경제·저장 등 중요한 규칙의 테스트
```

## 책임 분리 — 설계 제안

| 모듈 | 책임 | 맡기지 않을 일 |
| --- | --- | --- |
| `GameSession` | 활성 프로필·행성·현재 모드·전환 | 모든 게임 규칙을 한 파일에 수용 |
| `PlanetRuntime` | 활성 행성의 객체·자원·환경 상태 | 영구 기술 소유권 관리 |
| `InventoryService` | 자원 잔량, 예약, 이동, 소비 | UI를 통한 임의 재고 변경 |
| `ConstructionService` | 배치 조건, 비용 처리, 철거 | 재질·버튼 렌더링 |
| `CraftingService` | 제작 작업·입력·등급·완료 | 매 프레임 등급 재추첨 |
| `RobotController` | 상태 전이, 이동·작업 실행 | 계정 경제 직접 수정 |
| `JobScheduler` | 작업 후보·예약·우선순위 | 로봇 외형 처리 |
| `PowerSystem` | 공급·수요·가동률·충전 | 자원 없는 무한 가동 |
| `TerraformingSimulation` | 환경값·안정성 이력 | 판매 버튼·UI 상태 |
| `PlanetEvaluator` | 스냅샷 기반 점수·등급·가격 내역 | 실제 대금 지급 |
| `EconomyService` | 구매·판매·회수·정산 거래 | 애니메이션 완료에 지급 의존 |
| `EventService` | 발견·선택·보상 상태 | 화면 재진입 때 보상 재지급 |
| `SaveService` | 버전·저장·복원·거래 일관성 | 노드 경로를 영구 ID로 사용 |

이 목록은 책임 경계다. 처음부터 각각을 전역 싱글턴으로 만들 필요는 없다. 프로필·저장·장면 전환처럼 수명이 긴 소수 상태만 전역 후보로 두고, 행성 서비스는 행성과 함께 생성·해제한다.

UI는 명령을 요청하고 결과·실패 사유를 표시한다. 재고·현금·환경 상태의 직접 수정은 도메인 규칙을 통해서만 수행한다. 상태 변화는 신호 등으로 표현 계층에 전달하여 UI와 애니메이션이 같은 사실을 읽게 한다.

## 시뮬레이션과 시간 — 설계 제안

- 이동·충돌은 엔진의 물리 갱신에 맞춘다. 로봇 작업 탐색과 환경 변화는 별도의 고정 간격으로 계산한다.
- 초기 제안 주기는 작업 배정 0.5초, 환경 갱신 1초다. 실제 성능과 체감에 따라 데이터로 조절한다.
- 생산·연료 소비·환경 변화는 경과 시간을 반영한다. 프레임 수가 늘었다고 생산이 빨라지지 않아야 한다.
- 같은 갱신에서 입력 자원·전력 배분을 먼저 확정하고, 실제 가동한 작업의 산출과 환경 효과를 적용한다.
- 공급 부족은 우선순위가 명시된 일시정지로 처리하는 안을 제안한다. 전 시설의 가동률을 임의로 달리 계산하지 않는다.
- 위 초기 싱글플레이에서는 메뉴·정산 시 일시정지한다. 확장 협동에서는 개인 메뉴가 세계를 멈추지 않으며, 팀 전체 정지와 거래 스냅샷의 일관성을 별도로 처리한다. [협동 시간·저장](04-coop-networking-and-session-save.md).
- MVP는 게임이 꺼진 동안 생산하지 않는다. 나중에 오프라인 진행을 추가하면 비용·환경·안정성 이력까지 함께 계산하는 별도 설계가 필요하다.

## 로봇 이동과 건축 — 설계 제안

자원 노드의 작업 위치와 시설 접근 위치를 별도로 정의한다. 시설을 배치·철거할 때 이동 가능 정보와 작업 예약을 갱신한다. 건물마다 비싼 전체 경로 계산을 매 프레임 수행하지 않는다.

초기 유한 맵에서는 배치 그리드 기반 이동 가능 정보와 A* 경로를 제안한다. 경사·복잡한 표면이 필요한 월드로 확장하면 Godot 내비게이션 기반 이동과 비교한다. 서로 다른 경로 시스템을 동시에 완성하려 하지 않는다. 어떤 방식을 택해도 ‘경로 없음’을 게임 상태로 반환하고 UI에서 해결 사유를 보여 줘야 한다.

## 렌더링과 콘텐츠 — 설계 제안

Blender 모델을 게임용 파일로 내보내 Godot에서 재질·외곽선·조명을 완성한다. 자세한 제작 절차는 [아트 문서](../production/01-art-and-blender.md)에 둔다. 외곽선 구현은 대표 장면에서 가독성·성능을 비교하여 선택한다.

로봇·시설의 작업 상태와 환경값을 애니메이션·효과·음향에 연결한다. 저장은 실제 게임 상태를 기준으로 하며 파티클 재생 시간이나 UI 노드 상태를 핵심 진행 데이터로 저장하지 않는다.

## 구현 검증 — 설계 제안

- 프로젝트 열기·기본 실행·종료, 선택한 에디터 버전과 내보내기 호환성을 확인한다.
- 인벤토리 중복 소비, 제작 중복 완료, 평가 경계, 거래 재적용, 저장 복원은 의미 있는 자동 검증 대상으로 삼는다.
- 조작·채집·배치·경로 정체·로봇 충전·환경 변화는 실제 플레이로 확인한다.
- 첫 루프에서 로봇 1대, 이후 5~10대와 여러 시설을 함께 운영해 병목을 측정한다. 목표 FPS와 최대 로봇 수는 플랫폼 결정 후 확정한다.
- 렌더링·물리·경로·시뮬레이션·오디오 비용을 구분해 측정하고 확인된 병목을 최적화한다.
- 문서 변경 자체에 게임 자동 테스트를 추가하지 않는다. 문서 링크·용어·범위의 일관성을 검증한다.

## 1.2 렌더링 모듈

`FrontierGraphics`가 `data/graphics.json`의 화질을 Viewport·Environment·태양 그림자에 적용한다. `FrontierPlanetView`는 기존 GLB 재질의 이름을 보존해 금속·에나멜·차체·자연물·발광면을 구별하고, 지역 광원은 고정 6개 풀에서 프리셋 한도만 활성화한다. 건설·철거·행성 재생성 시 기존 조명 노드를 무한히 만들지 않는다. 지면·수면·하늘·암벽·위성 셰이더는 `assets/materials/`에 둔다. [적용 범위와 측정](../production/03-rendering-and-performance.md)이 렌더링 품질의 기준이다.

## 탐험 확장의 책임 경계 — 제안·미구현

| 영역 | 담당할 상태·명령 | 기존 구조에서 바뀌는 점 |
| --- | --- | --- |
| 은하·항해 | 단일 은하 ID·시드·성역·항로·현재 선박·항해 사건 | 지구↔행성 장면 전환보다 넓은 지속 세계 |
| 천체 생성 | 원천 카탈로그·티어·계층 시드·생성 매니페스트 | 원형+버전+변경분으로 재현 |
| 지역 월드 | 청크·지하·국소 굴착·좌표·활성/집계 전환 | 평면 맵 전체 상주를 대체할 후보 |
| 우주선·수송 | 개체·모듈·전력·질량/부피·생물실·선적 | 슬롯 등급을 실제 운송 상태로 확장 |
| 발견·연구 | 관측·가설·실험·원리·표본 | 일회성 보상과 반복 실험 작업을 분리 |
| 생태 | 사례 ID·계통·휴면·개체군·이식 구획 | 렌더 개체 수와 집계 생물량 구분 |
| 문명·협약 | 상대·권한·환경 목표·거래·위반·전환 | 일회성 선택을 이력 있는 상태로 확장 |
| 정산·저장 | 사업 범위·단계 지급·권리·자산 이전·버전 | 매각 한 번뿐 아니라 항해·선적·협약 거래 보존 |

구매 버튼만 탐사 버튼으로 바꾸지 않는다. 후보 조사→권한→착륙, 기지→우주선→새 기지의 자산 인계, 출발과 매각의 분리, 현재 지역과 보존된 여러 목적지의 수명이 먼저 성립해야 한다. 기존 도메인 중 제작·자원 예약·기본 로봇 작업은 재사용 가능성을 검토하되 경로·거래·저장 가정을 확인한다.

새 서비스명·폴더·엔진 플러그인은 확정하지 않는다. 상태·명령·검증 경계를 먼저 작은 실증으로 만들고 E0~E5 순서로 통합한다. 사례 생물의 모델·애니메이션 선택은 정의 데이터를 읽으며 게임 실행 중 외부 이미지·모델 생성 호출에 의존하지 않는다.

## 호스트 포함 6인 협동 — 목표·미구현

멀티플레이는 추가 확정 방향이다. 기존 로컬 단일 프로필·플레이어·활성 지역 가정을 그대로 여섯 번 복제하지 않는다. 개인 캐릭터/반입 장비, 호스트 세계/공동 장부, 접속 회차, 선체/승무원, 로컬 입력/확정 명령을 분리한다. 상세 경계는 [협동 네트워크·세션 저장](04-coop-networking-and-session-save.md)에 둔다.

호스트가 세계의 상태와 거래를 확정하고 게스트는 입력·작업을 요청한다. 조종 권한 위임은 네트워크 호스트 이전이 아니다. 호스트 플레이어가 보지 않는 지역도 다른 참가자가 있으면 유지하며, 모든 참가자의 관심 지역과 작업을 합산한다. 단일 시드 생성은 원형 재현에 쓰고 실제 변경분의 동기화를 대체하지 않는다.

E0에 호스트+게스트의 연결·자산·동시 작업·저장 실증을 넣고 E1 이전에 6인 정원과 공동 승선 기반을 검증한다. E2~E5의 지하·생물·문명·거래는 이 구조 위에서 확인한다. 기존 1.2의 813개 확인 항목은 네트워크·6인 성능 검증 근거가 아니다.
