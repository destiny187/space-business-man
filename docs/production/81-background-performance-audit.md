# 정지 상태의 백그라운드 CPU·렌더링 비용 조사

2026-09-09 사용자 요청: 지형 최적화 후에도 화면 대비 성능이 낮으므로 추가 최적화 여지를 찾는다. 기준 소스는 `6ed351a7`이다. 이번 작업은 **진단 도구와 조사 기록**이며 아래 제안을 제품에 적용한 것은 아니다.

후속: 사용자의 수정 승인 후 [백그라운드 갱신·저장 최적화](83-background-update-and-save.md)를 적용했다. 아래 수치와 미구현 표기는 수정 전 조사 시점의 기록이다.

## 핵심 결과

지상에서도 보이지 않는 우주 비행 장면의 `_process`가 계속 실행된다. 실제 첫 계측에서 평균 **4.20ms/프레임**, 두 번째 계측에서 **3.42ms/프레임**이었다. 우주 SubViewport의 렌더를 끄는 것과 그 안의 게임 스크립트 처리를 멈추는 것은 별개다. `presentation_blocked`는 소리·안내 일부를 막지만 공전, 카메라/선박 보간, 천체 조명과 표식 계산을 중단하지 않는다.

반면 정착이 끝난 지형 스트리머·원경의 콜백 시간은 합쳐 약 **0.006ms/프레임**이었다. 이는 정지 상태의 값이며 이동/굴착 비용이 사라졌다는 뜻은 아니다. 앞선 지형 최적화는 이동 때의 비용을 줄였지만 정지 상태의 다른 비용을 해결하지 않았다.

## 확인한 CPU 비용

| 대상 | 직접 계측 | 코드에서 확인한 원인 / 개선 방향 |
| --- | --- | --- |
| 숨겨진 우주 비행 화면 | 평균 3.42~4.20ms/프레임 | 지상에서도 공전·우주 카메라·표식·천체 조명 갱신. 표시가 필요할 때만 갱신하고 재진입 때 권한 상태로 즉시 복원 |
| 우주 공전 위치 갱신 | 평균 2.00ms/호출 | 현재 비행 화면의 행성/달 위치·자전과 재질 시간 업데이트. 위 우주 비행 비용에 포함 |
| 우주 천체 조명 | 평균 0.80ms/호출, 최대 18.32ms | 수신 재질별 가림 후보 생성/정렬/셰이더 전달, 선박 재질 재수집. 위 비용에 포함 |
| 우주 표식 계산 | 평균 0.49ms/호출 | 보이지 않는 우주 카메라로 정거장·목표·위험 표시를 다시 계산. 위 비용에 포함 |
| 항해 UI | 최초 평균 1.69ms/프레임 | 경로 인덱스 준비 중 `FrontierStellarRoutes.build()`가 매 프레임 약 1.5ms를 사용. 준비 완료 후 감소하므로 상시 비용으로 해석하지 않음 |
| 스냅샷 화면 반영 | 평균 3.64ms/호출, 최대 12.64ms | 약 10Hz 상태마다 우주 화면뿐 아니라 닫힌 조선소·정거장 거래·선박 단말 화면도 갱신. 최신 데이터 보관과 화면 재구성을 분리할 여지 |
| 세계 저장 | 1회 23.30ms | 물리 콜백에서 동기 저장. 현재 세계 검증, 임시 파일 기록/재읽기 검증, 이전 파일 재읽기 검증과 백업. 위 네트워크 물리 콜백에 포함 |
| 생물 모션·LOD | 평균 0.43~0.67ms/프레임 | 이 장면 12개 콜백 인스턴스 합계. 숨김/거리/비활성 LOD별 모션 준비를 줄일 후보지만 우선순위는 낮음 |

첫 계측의 상위 `_process`/`_physics_process` 합계는 평균 **11.85ms/프레임**이었다. 그중 우주 비행과 준비 중인 항해 UI가 약 절반이었다. 두 번째 계측에서는 경로 인덱스 **125,000개 준비 완료**를 확인했으므로, 그때 경로 준비를 제외한 실험은 사실상 변화가 없는 대조 조건이다.

**수치 해석:** 이 값은 메인 스레드 콜백의 경과 시간이다. 호출 안의 엔진 대기까지 포함하며 CPU 하드웨어의 순수 산술 시간이나 점유율은 아니다. 부모 콜백에 포함되는 세부 함수 시간은 합산하지 않는다. 표시한 경과 시간은 계측용 복사본의 기록이고 제품 코드에는 타이머를 넣지 않았다.

## 그래픽 자체의 비용 분리

Apple M2, Metal Forward+, 1280×800, 보통·100% 렌더, FPS/VSync 해제. 같은 현재 지상 장면에서 게임 처리를 멈춘 뒤 항목 하나씩 임시로 제외하고 복구했다. GPU 시간은 제공되지 않아 프레임 경과 시간을 측정했다.

| 진단 조건 | 평균 프레임 시간 |
| --- | ---: |
| 실제 진행 중 | 22.43ms / 44.6 FPS |
| 게임 처리 정지 | 13.18ms / 75.9 FPS |
| 정지 상태 + 렌더 해상도 50% | 5.84ms |
| 정지 상태 + 윤곽선 제외 | 10.58ms |
| 정지 상태 + 하늘 단순화 | 11.67ms |
| 정지 상태 + 지형 재질 단순화 | 11.66ms |
| 정지 상태 + 그림자 제외 | 12.96ms |
| 정지 상태 복구 | 13.12ms |

렌더 해상도와 픽셀 처리에 따른 부담도 있다. 윤곽선 제거는 승인된 INK 품질을 어기므로 제품 제안이 아니며, 같은 외곽선을 더 적은 연산으로 계산하는 후보를 찾기 위한 진단이다. 그림자는 드로콜을 크게 줄였지만 이번 조건의 프레임 시간 이득은 작았다. 후처리/지표 장식 제외에서는 시간이 오히려 늘어 결과가 불안정했으므로 비용 순위의 근거로 쓰지 않는다.

**정지 전후 완전히 같은 렌더 부하는 아니다.** 정지하면 애니메이션/입자 등의 처리도 달라지며 드로콜이 약 1,613→1,364로 변했다. 따라서 22.43−13.18ms를 순수 CPU 비용으로 단정하거나 현재 장면이 즉시 76 FPS를 낼 수 있다고 보장하지 않는다. 별도로 확인한 27개 SubViewport 중 우주/장비 미리보기는 대부분 업데이트가 꺼져 있었으며, 보이지 않는 모든 미리보기가 렌더되고 있다는 증거는 없다. 800×600 은하 뷰의 `WHEN_VISIBLE` 설정만으로 실제 렌더 중이라고 판단하지 않는다.

## 현재 진행을 유지한 추가 대조

게임 전체를 멈추지 않고 우주 화면의 시각 콜백만 제외하거나 경로 인덱스 준비만 제외했다. 권한 시뮬레이션/물리/지상 화면은 계속 진행하고, 각 항목을 복구했다. 시작 46.1 FPS, 우주 갱신+경로 준비 제외 49.3 FPS, 복구 47.2 FPS였다. 우주 갱신 단독 제외는 44.2 FPS로 오히려 낮아졌으며 장면·환경/OS 부하 변동이 있어 **이 실험만으로 확정적인 FPS 개선율을 주장하지 않는다.** 인덱스는 이미 준비 완료였다. 실제 콜백 비용과 코드상의 불필요한 계산은 확인했지만, 제품 수정 후 동일 조건의 짧은 재계측이 필요하다. ## 제안 우선순위

1. **표시하지 않는 우주 시각 갱신 중단.** 지상과 항해 지도가 우주 화면을 가리는 경우를 구분한다. 권한 항해/협동은 유지하며, 이륙·우주선 창/외부 시점·성간 이동 전환에는 즉시 최신 상태로 복원한다.
2. **지도 인덱스 준비와 닫힌 UI 갱신 분리.** 인덱스는 작업 스레드의 순수 배열 계산과 메인 스레드 반영으로 나누거나 사용 상황별 예산을 적용한다. 조선소/거래/단말 UI는 데이터가 바뀌거나 화면을 열 때 재구성한다.
3. **저장 경로의 메인 스레드 점유 축소.** 불변 스냅샷으로 직렬화·검증·파일 쓰기를 분리하되, 거래 성공/실패·원자적 교체·백업·종료 시 완료 대기를 유지한다. 단순히 검증이나 저장을 삭제하는 방식은 제안하지 않는다.
4. **윤곽선·하늘·지형 픽셀 연산 후속 개선.** 해상도 의존성이 확인됐지만 화질 기준을 유지하는 별도 비교가 필요하다. 그림자 해상도나 모델 세부를 일괄 줄이는 것을 최우선으로 두지 않는다.

## 재현과 범위

`python3 tools/prepare_performance_audit.py`는 이전 벤치마크의 격리된 `world.json/profile.json`을 복사하고, 임시 프로젝트의 68개 프레임/물리 콜백에 계측을 넣는다. 에셋/엔진 import 캐시는 링크로 재사용한다. 출력된 Godot 명령으로 기본 대조를 실행하며, `--targeted`를 추가하면 세부 함수 계측과 특정 백그라운드 처리 제외를 실행한다. 게임 소스와 실제 사용자 저장은 수정하지 않는다. 지표 고정 위치로 돌아간 격리 저장에서 진행했다.

이번 실제 실행은 지상 정지 장면의 원인 조사다. Windows·6인·장시간·이번 대조 조건의 보행/굴착 검증은 수행하지 않았다. 우주/지도 갱신 중단·비동기 저장은 **아직 제품 미구현**이다.
