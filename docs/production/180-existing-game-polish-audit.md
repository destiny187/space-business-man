## 조사 범위와 판단

기준 코드 `1bc57d50f`. 현재 기본 원정의 입력·가이드·사격·설정·저장 경로, 최근 제작/검수 기록, 기존 복원 전후 및 작은 연구 화면을 읽었다. **이번에는 게임을 실행하지 않았고 코드·밸런스·사용자 저장을 변경하지 않았다.** 아래의 코드 확인은 실행 재현과 다르다. 과거 성능 수치는 당시 조건의 참고 자료이며 현재 빌드 실측이 아니다.

이 게임에서 가장 먼저 선명하게 만들 경험은 **내가 모은 재료가 일을 대신하는 설비가 되고, 그 설비가 내가 머물던 장소를 바꾸며, 그 성과로 다음 원정을 선택하는 흐름**이다. 이 판단은 [게임 비전](../game/01-vision-and-loop.md)에 근거한 보강 제안이다. 전투의 타격감도 필요하지만 제작·자동화·복원의 성취가 약하면 핵심 경험을 대신할 수 없다.

기존 [복원 전](media/terraform-surfaces/progression/0-barren.png)과 [정착 후](media/terraform-surfaces/progression/3-established.png)를 이번에 직접 열어 비교했다. 지면과 식생의 변화는 명확하다. 따라서 환경 변화 자체가 없다는 진단은 맞지 않는다. 다만 준비된 현장의 단계별 렌더이므로, 보통 플레이에서 그 장면에 도달하는 시간·이유의 이해·성취감까지 확인된 것은 아니다. 상세 조건은 [134 제작 기록](134-terraform-surface-progression.md)을 따른다.

증거 표기는 다음과 같다.

- **코드 확인:** 현재 경로와 조건을 읽어 확인했다. 발생 빈도·체감은 미측정이다.
- **기록상 한계:** 이전 검수에서 명시적으로 남긴 범위다. 현재 오류라는 뜻은 아니다.
- **플레이 가설:** 플레이어의 관찰로 채택/기각할 품질 가설이다. 확정 버그로 취급하지 않는다.

## 우선순위

## 코드에서 확인한 보강 지점

### P1-01 — 발사 입력 보관은 이미 있고, 저장 대기의 체감은 별도다

관련 코드: [호스트 저장 확정](../../우주-비즈니스/scripts/network/crew_authority.gd)의 `request()`·`pump_requests()`·`resolve_autonomous()`·`step_surface()`, [사격 표시](../../우주-비즈니스/scripts/actors/firearm_view.gd)의 `shoot()`·`_response()`, [세션 응답](../../우주-비즈니스/scripts/network/crew_session.gd).

1. 단발 클릭은 `shoot()`에서 `surface_fire`를 전송한다. 발사 간격/꺼내기 중이거나 미응답 발사 4개에 도달하면 기존 `input_buffered`가 입력을 보관한다.
2. 일반 플레이는 `session.send_request()`→호스트 `request()`를 거친다. 저장 대기 중이면 사수별 발사 요청 한 건을 보관하고 `pending`을 반환한다. `pump_requests()`는 저장 완료 뒤 처리하며 0.8초를 넘긴 발사는 `trigger_expired`로 폐기한다. 추가 발사에는 `trigger_buffer_full`이 반환될 수 있다.
3. 실행할 때 장비/입력 허용 등을 다시 검사한다. `step_surface()`는 저장이 미확정이면 탄도 `ballistics.step()`에 도달하기 전에 반환한다. 입력 보관이 있어도 발사 확정·탄도 진행에 저장 대기가 개입하는 구조는 남아 있다.

**저장 중 단발을 무조건 버리는 버그는 현재 일반 경로의 결함으로 올리지 않는다.** [166](166-firearm-ammunition-and-ballistics.md)에 이 입력 보관의 구현과 탄도 대기 한계가 명시돼 있다. [169 후속 검수](169-firearm-precision-and-laser.md)의 `weapon_blocked` 기록이나 하위 `firearm_command()`만으로 일반 요청 경로의 버그를 단정할 수 없다. 이번 조사 과정의 초기 의심은 상위 경로 확인 후 정정했다.

플레이에서 지연이 느껴지면 클릭→대기→호스트 발사→명중 시점을 나눠 측정하고 저장 제출/대기 원인을 먼저 줄인다. 버퍼를 늘리거나 만료 요청을 무조건 재시도하는 해결은 뒤늦은 발사를 만들 수 있다. 기존 보관 상한·현재 장비/입력 재검사·호스트의 탄약/피해 확정을 유지한다. 대기 만료의 빈도, 실제 입력 지연·탄도 멈춤의 체감은 이번에 측정하지 않았다.

### P1-02 — 비동기 저장 이후에도 전체 가변 상태의 검증·복사가 남는다

관련 코드: [저장소](../../우주-비즈니스/scripts/persistence/world_store.gd)의 `begin_commit()`, [스냅샷](../../우주-비즈니스/scripts/persistence/world_snapshot.gd)의 `copy()`, [호스트](../../우주-비즈니스/scripts/network/crew_authority.gd)의 `step_surface()`·`_step_surface()`.

`begin_commit()`는 메인 스레드에서 `validate_world()`와 `WorldSnapshot.copy()`를 실행한 뒤 작업 스레드에 제출한다. 불변 manifest는 공유하지만 다른 가변 분기는 깊은 복사 대상이다. 산업 진행은 1초마다 세계 초안을 만들고 운영 중 현장을 순회한다. 현장을 함께 생산하는 순회 자체에는 이유가 있지만, 개별 행동의 검증/복사 비용까지 세계 이력에 비례하는 부분은 분리할 여지가 있다.

지표 스캔 코드의 `save_world.call()`만 보고 동기 파일 저장이라고 판단하면 안 된다. 현재 세션은 `step_surface()`에서 이 콜백을 후보 기록으로 잠시 교체하고, 최종 후보를 `save_autonomous`로 비동기 제출한다. 실제 남은 문제는 전체 가변 초안·제출 비용과 확정 대기다.

[160](160-transaction-drafts.md)의 개인 장비 부분 초안·일반 거래 비동기화는 이미 구현됐다. [147](147-ground-frame-budget.md)의 당시 M2/1280×800/보통 계측은 보행 평균 약 29~34 FPS, 일부 100ms 초과 프레임을 기록했다. **리모델링·후속 변경 전 수치이므로 현재 FPS라고 말하지 않는다.** 새 조사에서는 사용자 제보 장소와 행동을 기준으로 한 번의 프레임 지연을 먼저 측정해야 한다.

입력→변경 분기→검증/복사→저장 확정→패킷 구성→열린 UI/모델 갱신 순으로 추적한다. 실패/중복 요청·닫힌 화면도 함께 보되, 전체 회귀 묶음으로 확대하지 않는다. 원자 저장·중복 지급 방지·협동 일관성은 유지한다.

### P2-01 — 키 변경 기반과 현재 원정 입력 경로가 분리돼 있다

[input_bindings.gd](../../우주-비즈니스/scripts/app/input_bindings.gd)에 키 변경 기능이 있고 [구형 main.gd](../../우주-비즈니스/scripts/app/main.gd)에 해당 설정 UI가 남아 있다. 그러나 현재 [crew_expedition.gd](../../우주-비즈니스/scripts/app/crew_expedition.gd)의 보행 WASD·Shift, 스캔 E/F, 비행 W/S/Q/E/Space/Alt와 여러 메뉴 키는 물리 키를 직접 읽는다. 점프·로버 일부 입력만 기존 액션을 함께 사용한다.

현재 원정의 [client_settings.gd](../../우주-비즈니스/scripts/ui/client_settings.gd)는 감도·FOV·세로 반전·사건 흔들림·전체/음악 음량을 제공한다. 이 메뉴에는 키 재설정, UI/글자 배율, 조준/질주 유지·전환 선택, 독립 효과음 음량 설정이 없다. 이 사실을 게임 전체에 설정 기능이 전혀 없다는 뜻으로 확대하지 않는다.

후속에서는 현재 원정의 행동 단위로 입력을 모으고 안내 표시도 같은 매핑을 사용해야 한다. 단순히 설정 버튼만 추가해서는 해결되지 않는다. 기존 조작을 기본값으로 유지하고 충돌 검사·취소·기본값 복원을 제공한다. 접근성 옵션의 구체적인 목록/값은 보강 제안이며 이번에 확정하거나 구현하지 않았다.

### P2-02 — 감도·음량 한 번의 변경이 전체 장면 설정을 적용한다

[client_settings.gd](../../우주-비즈니스/scripts/ui/client_settings.gd)의 `set_option()`은 화면 모드/해상도 외의 항목마다 `apply_all()`→`save_settings()`→`_sync()`를 실행한다. `apply_all()`은 전체 장면 트리를 재귀 순회해 뷰포트·카메라·환경·조명 설정을 적용하고 공통 `changed` 신호를 발행한다. 감도 슬라이더의 각 `value_changed`에도 동일 경로가 연결된다.

[surface_hydrology.gd](../../우주-비즈니스/scripts/world/surface_hydrology.gd)는 이 신호를 받아 수질 설정을 다시 읽고 수면 재질/바다 메시를 재지정한다. 따라서 감도 변경은 감도 값만 바꾸는 행동임에도 그래픽 설정과 수면 처리를 건드린다. 이로 인한 실제 프레임 하락이나 메시 신규 생성 횟수는 계측하지 않았다.

항목별 적용 대상을 분리하고 변경 없는 값은 생략하는 것이 우선이다. 슬라이더는 즉시 체감값을 반영하되 디스크 저장은 조작 종료 등 명확한 경계에서 합치는 방안을 검토한다. 화면 변경의 15초 복구와 저장 실패 안내는 보존한다. 이번에는 조사만 했으므로 범위 축소가 완료됐다고 기록하지 않는다.

## 실제 플레이에서 판단할 품질 가설

### P1-03·04 — 자유 플레이의 첫 목표와 자동화의 효용

[first_departure.gd](../../우주-비즈니스/scripts/ui/first_departure.gd)는 기본 조작·항해·착륙·채집기 장착·첫 채집을 안내한다. 지상에서 성공 응답의 `gains`에 양수가 들어오면 가이드 완료를 저장한다. 이후 제작·자동화·정산까지의 필수 안내가 없는 것은 [자동화 선택 원칙](../game/03-robots-and-automation.md)과 일치하며 그 자체는 버그가 아니다.

확인할 것은 **안내가 사라진 뒤에도 플레이어가 기존 메뉴와 현장을 보고 스스로 목적을 정할 수 있는가**다. 다음 설비의 효용, 부족한 재료의 보관 위치, 로봇이 대기하는 원인이 같은 맥락에서 읽히는지 본다. 새로운 강제 튜토리얼 대신 기존 선택 상세·설비 상태·지도 연결을 보강하는 방향을 우선한다. 이미 있는 검색·가능 필터·보급 계획을 다시 만들자는 제안은 아니다.

[109 진행 측정](109-t3-progression-benchmark.md)은 선박 진입 조건 변경 전의 자동 조작 기록이다. 당시 1인 보행 11분 06초와 채집 동작 41.2초는 이동 비중을 살펴볼 단서지만, 현재 초보자의 체감이나 단순 낭비 시간을 증명하지 않는다. [116 선박 조건](116-vessel-tier-access.md)과 [156 제작소/연구 변경](156-start-and-field-polish.md) 이후의 수동 완주 리듬은 별도로 봐야 한다.

첫 로봇 전후에 같은 자원을 얻는 데 필요한 직접 작업·반복 왕복·메뉴 횟수가 어떻게 달라지는지 관찰한다. 불필요한 왕복이 확인되면 기존 수납/출고 위치·일괄 수량·작업 선택·비용/소요시간을 조정한다. 자동 운송이나 새로운 생산 체계의 추가로 범위를 넓히지 않는다. 빠르게 끝내는 것만이 목표는 아니며 이동 중 발견·판단이 있었다면 유효한 플레이로 구분한다.

### P1-05 — 환경 변화가 플레이어 자신의 성과로 읽히는가

확인할 연결은 설비 설치→전력/원료 공급→실제 환경 개선→눈에 보이는 변화→단계 지급/계약 선택→다음 투자다. 이미 있는 환경 레이어·보급 계획·국소 녹지·우주 외형·시설 보유/인계 정산을 활용한다. 현재 정산 화면에는 자산 인계와 보유 선택의 설명/확인이 있으므로 안전장치 부재로 진단하지 않는다.

복원이 멈췄을 때 원료·전력·환경 조건 중 무엇이 원인인지 찾기 어려운지, 변화가 너무 늦거나 갑자기 완성돼 내 작업과 연결되지 않는지 본다. 복원한 장소로 돌아왔을 때 만족감이 있고 정산 이후의 투자 목표가 생기는지도 기록한다. 보강은 기존 효과의 시점·성장 밀도·가동 상태·정산 결과 표현을 다듬는 범위다. 진행하지 않은 환경을 연출만으로 앞당기지 않는다.

### P2-03 — 동작의 자연스러움, 전투의 공정함, 음향 피로

[177 고속 모션](177-creature-fast-motion-rollout.md)·[178 비행종/제트팩](178-flying-wildlife-and-jetpack.md)·[169 총기](169-firearm-precision-and-laser.md)·[179 우주 피격](179-space-damage-feedback.md)의 연결과 대표 검수는 이미 있다. 전종 개별 미적 검수, 직접 손 조작, 장시간 청감/밸런스는 같은 의미의 완료가 아니다.

- 생물이 빨라져도 발 접지·선회·공격 준비와 회수 동작을 읽을 수 있는가. 개선을 위해 실제 이동속도를 낮추지 않는다.
- 맞은 원인과 피할 기회를 이해할 수 있는가. 이를 대응법 설명 HUD를 되살리는 방식으로 해결하지 않는다.
- 총기·채광·제트팩·선박 추진의 반복 소리가 피로하지 않은가. 위험음과 실드 파괴음이 배경음악/추진음에 묻히지 않는가.
- 같은 환경에서 원경의 윤곽·식생 밀도·근접 생물과 시설의 표현이 한 장면으로 조화로운가. 전투 효과 때문에 대상이 가려지는가.

음원 파일과 출력/클리핑 검사만으로 듣기 좋은 믹스가 확정되지는 않는다. 먼저 기존 음원의 레벨·거리·중첩·반복 경계를 다듬는다. 새로운 소리가 실제로 필요한 경우에만 ElevenLabs 제작 범위를 별도로 잡는다.

### P2-04 — 협동과 복귀는 구현 여부보다 경험의 차이를 봐야 한다

협동 기반·재접속·개인 장비·FINCH 독립 출동은 구현돼 있고 [169](169-firearm-precision-and-laser.md)의 6개 ENet 연결 확인도 있다. 다만 최신 모든 기능의 6인 외부망 품질을 보장하는 자료는 아니다. 오늘 사용자의 솔로 테스트를 협동 검사로 확대할 필요는 없다.

협동 플레이 기회가 생기면 호스트만 메뉴/조종/운반을 담당하는지, 동료의 작업 완료와 공동 비용을 이해할 수 있는지, 승선/출항 대기가 목적 없는 시간으로 남는지를 본다. 실패 복귀에서는 위치·화물·장비·진행을 추측하지 않아도 되는지가 중요하다. 발견된 특정 문제만 작은 저장 사본이나 최소 접속 구성으로 재현한다.

## 사용자 플레이 메모

검사표를 전부 채우기보다 자연스럽게 플레이하다 **처음 막힌 순간, 반복이 귀찮아진 순간, 내 선택의 결과가 좋았던 순간**을 남기는 편이 유용하다. 재미있던 부분도 있어야 보강 중 지켜야 할 것을 알 수 있다.

| 순간 | 짧게 남길 내용 |
| --- | --- |
| 출항·첫 착륙 | 무엇을 하려 했고 어느 지점에서 목적/조작을 놓쳤는지 |
| 채집·제작·운반 | 반복 왕복의 이유, 재료가 있는데 못 썼던 위치, 메뉴를 다시 연 이유 |
| 첫 로봇·설비 가동 | 무엇이 편해졌는지, 대기 이유를 알아냈는지 |
| 전투·제트팩 | 사용 장비, 저장/메뉴 직후 여부, 입력 무반응 또는 맞은 이유를 모른 순간 |
| 복원·정산 | 처음 변화를 알아본 순간, 그 원인이 이해됐는지, 다음에 하고 싶어진 일 |
| 종료·이어하기 | 기대했던 위치·장비·화물·진행과 실제 차이 |

복사해서 쓸 최소 양식:

```text
새 원정/이어하기 · 솔로/게스트 · 행성/장소:
하려던 행동:
기대한 결과 → 실제 결과:
느낌: 재미 / 막힘 / 번거로움 / 불공정 / 만족
대략적인 시점·화면/영상이 있으면 위치:
```

첫 관찰만으로 경제 전체를 재조정하지 않는다. 조작 실수·안내 부족·실제 규칙 문제·성능 지연을 분리하고, 같은 문제의 빈도와 핵심 루프에 미치는 영향으로 우선순위를 갱신한다.

## 다음 작업 제안과 완료 경계

최신 실행 순서는 [Q01~Q09 고도화 계획](../planning/17-existing-play-polish-plan.md)을 따른다. 설정 적용 범위·입력·저장 반응성부터 기존 목표 선택·자동화·복원·전투/음향·협동까지 개발자가 먼저 연결하고 최소 확인한다. 사용자 관찰은 병목과 체감 품질을 보정하는 추가 근거다.

이 조사와 후속 계획은 **문서화 완료** 상태다. 게임 수정·새 콘텐츠 제작·현재 FPS 재측정·실제 플레이 완주·사운드 청감·6인 외부망 검증을 완료한 것으로 기록하지 않는다. 세부 수치는 개발자의 실제 확인과 사용자 플레이 관찰을 반영해 조정한다.
