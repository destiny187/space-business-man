# 현재 원정 성능 종합 점검 — 2026-09-12

**판정: 최적화는 유효하지만, 아직 쾌적한 플레이가 확보됐다고 보기 어렵다.** 평균 FPS뿐 아니라 생물 보행, 시설 생산·지표 상태 갱신, 지상 지도에서 긴 프레임이 확인됐다. 이번 작업은 점검이며 게임 기능·그래픽·음원·사용자 저장을 수정하지 않았다.

## 실제 확인 범위와 측정 조건

- Apple M2 / 메모리 24GB / Godot 4.7.2 / Metal Forward+, 실제 1280×800 창, 기존 보통 옵션·2× MSAA·100% 렌더. VSync/FPS 제한 해제. 60 FPS의 프레임 예산 16.7ms는 비교 기준이며 확정된 최소 사양을 의미하지 않는다.
- HEAD `100cc2f52`와 미커밋 변경을 포함한 현재 scripts/data/scenes를 별도 실행 폴더에 복사했다. 기존 제작 에셋과 import 캐시는 재사용했다. 소스 해시는 [source-state.json](source-state.json)에 남겼다. 측정 중 별도 작업으로 field_instruments.gd, firearm_view.gd, firearm_effects.gd, firearms.gd, firearm_feedback.json이 변경됐다. 마지막 작업 트리 전체를 다시 측정한 결과는 아니며, 위 네 병목의 직접 소스는 점검 시작 때와 동일했다.
- 기존 격리 벤치마크 저장의 복사본으로 생물 지상과 시설 7개 지역의 정지·보행·지도/사업 화면을 실행했다. 해당 저장의 기존 행성 생성 규칙을 유지한다. 새 은하 전체·새 착륙 연출을 이 결과로 검증한 것은 아니다.
- 기본 측정과 함수 계측 실행은 분리했다. 계측은 임시 프로젝트의 콜백과 선택한 함수를 감쌌으며, CPU 비용의 위치를 찾는 자료다. 중첩된 함수 시간을 더해서 전체 프레임 비용으로 계산하지 않는다. 엔진 Performance 모니터는 벽시계 프레임과 갱신 시점이 달라 합산하거나 같은 프레임의 정확한 원인으로 취급하지 않는다.
- 마우스 자동 캡처만 진단 복사본에서 해제했다. 실제 게임 로직과 지형·호스트·저장·모델 처리는 계속 실행했다. 전용 사용자 설정 경로와 격리 저장을 사용했다.
- **공유 PC 부하가 컸다.** 실행 중 Chrome Renderer 117.5% CPU와 WindowServer 등의 부하, 도구 응답 지연을 관찰했다. 첫 중단 실행은 결과에서 제외했다. 생물 지역의 낮은 FPS를 순수한 게임 회귀율이나 다른 PC의 성능으로 일반화하지 않는다. 측정 환경의 swap은 0, 조회한 thermal/performance warning 기록은 없었다. 온도·클럭을 직접 측정한 것은 아니다.
- GPU 타이머는 0을 반환해 `null`로 기록했다. GPU 셰이더별 ms는 미확정이다. 이 보고서의 병목은 코드와 함수 계측을 함께 근거로 판단했다.

## 우선순위가 높은 잔여 병목

### 1. 생물의 새 발 접지 계산이 기존 가시성 생략 밖에서 실행됨

생물 지역 정지 계측에서 `surface_ecology._process`가 프레임당 11.07ms, 그 안의 `_update_wildlife`가 호출당 평균 10.76ms였다. 보행에서는 `_update_wildlife` 평균 17.70ms·최대 190.25ms였다. 후자의 최대값에는 시스템 스케줄링·캐시/지형 이동의 영향도 포함될 수 있다. 개별 발 함수 전체가 그 시간을 차지한다고 단정하지 않는다.

코드는 활성 현장 생물마다 매 프레임 `drive_ground`를 호출한다. 기존 `bestiary_actor._process`의 화면 가시성 검사는 별도 경로이고, `drive_ground → ground_locomotion.drive → advance → Feet.update`에는 같은 가시성 검사가 없다. 발 접지는 심지어 정지한 발도 주기적으로 지형을 다시 조사한다. 호스트의 실제 위치·충돌·전투 판정을 유지하면서 시각적 발 접지 갱신에 화면/거리별 예산, 지형 수정 시 갱신, 복귀 시 접지 복원을 연결하는 것이 우선이다.

근거: [현장 생물 갱신](../../../../../우주-비즈니스/scripts/world/surface_ecology.gd), [가시성과 별도 보행 호출](../../../../../우주-비즈니스/scripts/actors/creatures/bestiary_actor.gd), [발 접지](../../../../../우주-비즈니스/scripts/actors/creatures/ground_locomotion_feet.gd), [정지 계측](profile-ground/medium-cpu.json), [보행 계측](profile-ground/medium_walk-cpu.json).

### 2. 시설 생산의 매초 동기 저장과 메인 스레드 검증

시설 지역 보행 12초에 `world_store.write`가 12회, 평균 42.20ms·최대 47.53ms였다. `crew_authority.step_surface`는 생산 중인 현장을 처리하고 매초 동기 저장한다. 최근 해적 전투의 2초 체크포인트를 비동기로 바꾼 개선과 다른 경로다. 정지해도 생산이 계속되므로 이 지연은 이동 여부와 관계없이 남는다.

주기 체크포인트 역시 디스크 쓰기만 작업 스레드에 넘긴다. 제출 전에 수행하는 세계 검증·복사 등의 비용으로 `begin_checkpoint`가 약 20~24ms를 사용했다. 비동기 저장을 적용했다는 이유로 메인 스레드 비용이 없어진 것은 아니다.

다음 변경은 생산 진행과 거래 확정의 내구성·순서·실패 처리를 보존하면서 저장 제출을 모으고, 반복 검증/복사와 완료 처리를 분산하는 것이다. 저장이나 검증을 생략하는 해결책은 아니다.

근거: [생산·저장 경로](../../../../../우주-비즈니스/scripts/network/crew_authority.gd), [체크포인트 제출](../../../../../우주-비즈니스/scripts/persistence/world_store.gd), [시설 보행 계측](profile-industry/medium_walk-cpu.json).

### 3. 지표 패킷 생성·해시·화면 반영 비용이 그대로 남음

시설 보행의 `_publish_surface`는 23회, 평균 49.38ms·최대 70.64ms였다. 사업 화면을 연 구간에서는 평균 64.00ms·최대 113.43ms였다. 이 시간에는 호스트 자신의 화면으로 보내는 동기 신호와 화면 반영이 포함되므로 네트워크 직렬화 단독 비용이 아니다.

이미 개선한 이동 스냅샷의 공통 계산/변경분과 지표 패킷 경로는 다르다. 지표는 수신자별 전체 로컬 패킷을 만든 뒤 해시를 계산해야 변경 없음이 판정된다. 한 명인 싱글에서도 비용을 지불하며, 여러 참가자는 같은 발행에서 순서대로 처리한다. 열린 사업 화면의 `_surface_packet` 반영 자체도 평균 45.05ms였다(닫힌 보행 구간 11.11ms).

지표의 변경 영역·상태 revision을 먼저 확인하고 공통 자료를 공유하며, 열린 메뉴의 바뀐 수치/카드만 갱신하는 개선이 필요하다. 실제 6인 비용을 단순히 6배로 환산하지 않는다.

근거: [지표 발행](../../../../../우주-비즈니스/scripts/network/crew_session.gd), [지표 패킷](../../../../../우주-비즈니스/scripts/network/crew_surface_replica.gd), [화면 적용](../../../../../우주-비즈니스/scripts/app/crew_expedition.gd), [열린 사업 화면 계측](profile-industry/business_open-cpu.json).

### 4. 지상 지도에 약 0.84초의 메인 스레드 작업

지상 지도를 연 구간에서 `planet_map._process` 단일 콜백 837.71ms가 기록됐다. 계측 실행의 해당 구간 최장 프레임은 944.74ms, 별도 비계측 실행에서도 지도 구간에 1,070.11ms 프레임이 있었다. 두 값이 같은 실행의 동일 원인이라고 혼동하지 않는다. 적어도 지도 처리 자체의 긴 콜백은 직접 확인됐다.

`refresh()`는 160×100 픽셀마다 높이를 3번 조회한다(총 48,000회). 첫 표시·줌·드래그/크기 변경으로 키가 바뀌면 이를 메인 스레드에서 한 번에 다시 수행한다. 이 생성/캐시 경로를 분할하거나 작업 스레드에서 순수 자료를 만들도록 바꾸고, 이미 만든 지도는 상태·위치가 바뀐 부분만 갱신하는 것이 다음 순서다.

근거: [지상 지도 코드](../../../../../우주-비즈니스/scripts/ui/planet_map.gd), [지도 계측](profile-ground/navigation_open-cpu.json).

## 우주 전투·고해상도 렌더 경계

현재 복사본의 새 전투 세계에서 대기 5초·실제 3함선 교전 14초·동시 격파 4.5초를 실행했다. 실제 미사일/효과 표시와 호스트/체크포인트 진행 5개 확인은 통과했고 엔진/스크립트 오류는 없었다. 미사일 최대 4발·동시 격파 효과 최대 177개를 확인했다. 이 검사 스크립트는 앱의 일반 물리 입력 수집을 끄고 자동 조준/발사 입력을 직접 호스트에 보낸다. 호스트 물리·전투·저장과 화면 처리는 유지한다.

| 현재 전투 표본 | 평균 FPS | p95 | 최장 프레임 |
| --- | ---: | ---: | ---: |
| 대기 | 13.0 | 144.0ms | 153.7ms |
| 교전 | 7.1 | 204.3ms | 1358.1ms |
| 동시 격파 | 11.6 | 158.1ms | 197.9ms |

[현재 원자료](pirate/review-medium-1280.json). **이 표본은 기존 결과와 비교 가능한 대표 FPS로 채택하지 않는다.** 공유 PC의 높은 다른 앱 부하·도구 응답 지연과 함께 큰 악화가 관찰됐고, 게임/렌더러/OS 중 어느 원인이 얼마를 차지했는지 분리하지 못했다. 이는 측정 오차로 확정했다는 뜻도, 게임 회귀로 확정했다는 뜻도 아니다. 원인 미확정으로 보존한다.

직전 [146 성능 기록](../../../146-pirate-performance.md)은 보통 교전 평균 1280×800 49.2 FPS / 1920×1080 31.6 FPS, 1080 동시 격파 25.0 FPS였다. 이 기록만으로도 1080p 원본 해상도의 여유가 충분하다고 보기 어렵다. 화면 전체 픽셀·구름/대기·윤곽/후처리·폭발의 겹침 비용은 후속 분리 조사 대상으로 남는다. GPU 타이머가 없고 이번 재측정이 오염됐으므로 특정 셰이더의 ms 또는 현재 1080p FPS를 확정하지 않는다.

## 이미 줄어든 비용과 별도 경계

- 불변 은하/행성 정의 재사용, 이동 스냅샷 공통 자료·변경분, 숨긴 우주 화면의 갱신/렌더 생략, 정적 미리보기, 모델 생성 분산, 광물 메시 병합, 지형 작업 스레드·설치/해제 예산은 현재 코드에 남아 있다. 이번 지상 측정에서 숨긴 우주 뷰의 렌더 CPU 값은 0이었다. 기존 개선이 모두 무효화됐다는 뜻은 아니다.
- 지형 메인 처리 최대는 이번 시설 비계측 실행에서 약 5.38ms였지만, 생물 보행 계측에서는 약 17.05ms가 있었다. 단일 자원 설치/교체 호출을 예산 중간에 끊는 것은 아니므로 3ms 예산을 모든 프레임의 상한으로 해석하지 않는다. 모든 긴 프레임을 지형 메시 생성 탓으로 돌릴 수도 없다.
- 지상 렌더의 엔진 정적 메모리는 약 1,052~1,094MiB, 렌더 메모리 모니터는 약 649~691MiB였다. M2 통합 메모리에서 이들을 단순 합산하지 않는다. 두 짧은 비계측 실행은 엔진 오류/종료 누수 경고 없이 끝났으며, 시설 함수 계측 실행에는 ObjectDB 1개 종료 경고가 있었다. 장시간 메모리 누수를 확인/부정한 결과는 아니다.
- 실제 신규 세계 첫 착륙, 굴착 연속 작업, 대규모 로봇/시설, 날씨/지상 교전 집중 장면, 6인 독립 행성 플레이, 인터넷 지연/손실, Windows 실기·1440p/4K·장시간 열 부하는 이번 실측 범위 밖이다. 관련 코드는 확인했지만 이 조건의 성능 통과로 기록하지 않는다.

함수 계측 및 GPU 비용 해석은 [Godot CPU 성능 조사](https://docs.godotengine.org/en/stable/tutorials/performance/cpu_optimization.html), [GPU 성능 조사](https://docs.godotengine.org/en/stable/tutorials/performance/gpu_optimization.html)의 구분을 따른다. 계측 도구 자체의 오버헤드와 하드웨어별 렌더 차이를 고려했다.
