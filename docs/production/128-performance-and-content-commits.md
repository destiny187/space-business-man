## O01 — 먼 거리의 내부 선

깊이 55m 이후 내부 명암선의 기여도가 0일 때 여덟 방향 법선·깊이와 중앙 법선의 읽기를 생략한다. 가까운 내부 선, 외곽선, 깊이/폭/색 기준과 투명 합성 순서는 유지한다. 설정의 실제 `crease_fade.y`를 읽으므로 다른 거리 기준도 따른다.

Godot 4.7.2 Metal Forward+ / Apple M2 / 960×640에서 실제 채광 로봇 모델 네 개를 원근/정사영과 거리 12/54/56/85m로 렌더했다. 변경 전 셰이더와 8개 조건의 2픽셀 간격 RGB 표본 차이는 모두 0이었다. 대표 근거리와 원거리 이미지를 직접 확인했다. 이는 이미지 동등성 확인이며 전체 게임 FPS 개선율 측정이 아니다.

검수 자료: `output/optimization-20260911/contours.json`, `contours.log`, `contour-*.png`. 게임 자산 원본·형상·음원은 변경하지 않았다. 이후 단계는 필요한 실행·화면·소리 확인만 수행하고 별도 버그가 있을 때 관련 검사를 좁혀 실행한다.

추가로 기존 경사면·투명 배치 고스트·실제 풀링 효과의 GPU 확인 3개를 실행해 실패 0을 확인했다(composition.log).


## O02 — 지형 청크 해제 분산

관심 구역 변경 시 바깥 청크를 즉시 전부 해제하지 않고 대기열에 둔다. 프레임당 최대 두 건의 분리/해제를 기존 3ms 설치 예산 안에서 시작하며, 다시 관심 구역에 들어온 청크는 보존한다. 굴착으로 교체된 청크는 시각·충돌·가림막을 함께 분리한 뒤 자원 해제를 다음 프레임들로 넘긴다. 충돌 준비 후 예산을 재확인하고, 굴착 묶음의 원자적 교체는 유지한다.

새 검사용 T1 원정에서 실제 Forward+ 지상 진입, 35.2m 이동, 관심 구역 변경과 해제 대기열 소진, 굴착 묶음 교체, 현재 채집기와 음원/효과 연결, 저장까지 9개 확인에서 실패 0이었다. 이동 전후와 굴착 화면을 직접 확인했다. 이 검사는 음원의 청취 검사가 아니며 일반 행동 규칙은 변경하지 않았다.

검수 자료: `output/optimization-20260911/field-retire.log`, `field/terrain.json`, `field/walk.png`, `field/excavation.png`. 이전 검사용 저장은 최신 생태 원형과 맞지 않아 사용하지 않고 새 저장을 만들었다. 사용자 저장은 건드리지 않았다.

한계: 엔진의 단일 자원 생성/해제 호출과 굴착 묶음 교체를 중간에 끊지는 않는다. 이번 실행의 지형 메인 처리 최대는 39.499ms, 개별 교체 최대는 2.629ms였다. 모든 프레임이 3ms 이하라는 의미가 아니며 지형 순간 지연의 완전한 해결로 기록하지 않는다.


## O03 — 거래 초안의 은하 원형 공유

호스트가 보유하는 은하 manifest를 별도 소유본으로 만들고 내부 배열·사전까지 읽기 전용으로 고정한다. 거래와 체크포인트는 재고·행동·진행·영수증을 독립 복사하고 이 불변 원형만 공유한다. 동일 참조의 해시·JSON을 최대 네 개까지 재사용한다. 외부의 가변 원형, 다른 참조, 캐시에서 퇴출된 원형은 기존의 전체 복사/해시 경로로 돌아간다. 저장 버전·내용과 검증 항목은 유지한다.

거래는 여전히 임시 파일 쓰기·읽기 비교·JSON 검사·백업·교체를 끝낸 뒤 성공한다. 체크포인트 작업자는 메인 스레드에서 포착한 원형 문자열과 독립 진행 상태만 받으며, 공유 캐시에 접근하지 않는다. JSON 필드 순서는 달라질 수 있지만 복원된 상태는 동일하다.

검사: 기존 백그라운드 저장의 순서·백업·손상 복구·I/O 실패 검사와 새 불변 원형/초안 격리 검사 각각 14개에서 실패 0. 후자는 실제 호스트 준비 거래의 저장 완료, 저장 실패 시 상태/영수증 불변, 체크포인트 격리, 잘못된 원형 교체의 거부와 캐시 퇴출을 포함한다. `tests/check_world_snapshot.gd`에 저장 무결성과 관련된 작은 검사를 보존한다.

검수 자료: `output/optimization-20260911/background-save.log`, `world-snapshot.log`. 같은 새 원정(원형 JSON 26,958자)의 복사 30회는 기존 7,333µs, 공유 방식 259µs였다. 성장한 세계의 전체 저장 지연이나 FPS 개선율은 측정하지 않았다. 변경되는 사업·생태 상태는 계속 독립 복사하며 디스크 쓰기도 유지한다.


## O04 — 공통 계산과 확인된 기준 상태의 변경분

한 번의 상태 발행에서 선박·연구·모션·공급 현황 등의 공통 자료를 한 번 계산하고 참가자별 시점·재고·FINCH 맥락을 따로 구성한다. 송신자와 수신자는 최근 여덟 상태만 보존하며, 수신자가 검증 후 확인한 순번에 대해서만 중첩 사전 변경/삭제를 전송한다. 확인되지 않은 순번은 기준으로 사용하지 않는다. 기준이 만료되면 다음 발행부터 전체 상태를 보내고, 이전 세션의 기준은 재사용하지 않는다.

900바이트 조각과 완성된 프레임의 검증, 최대 전송 크기는 유지한다. 변경분이 전체보다 크면 전체를 보낸다. 배열은 부분 인덱스 갱신 대신 값 전체를 교체한다. 네트워크 프로토콜만 4로 올려 이전 실행판과의 혼합 접속을 차단하며 세계 저장 버전은 유지한다.

최소 확인: 실제 현재 호스트 상태로 조각 역순 수신, 중간 프레임 누락, 필드 삭제, 변형된 패치 거부, 수신 화면과 기준 상태의 격리, 만료 후 전체 복구 등 15개에서 실패 0. 같은 이동 상태 10회의 압축 페이로드는 기존 25,715바이트, 변경분 1,961바이트였다. 별도 로컬 ENet 호스트/참가자의 대기실 합류·시작·변경분 수신·종료도 통과했고 최대 조각은 900바이트였다.

검수 자료: `output/optimization-20260911/snapshot-delta.log`, `network/host-result.json`, `network/guest-result.json`. 첫 연결 확인 도구가 대기실 상태를 너무 일찍 종료 판정해 이를 바로잡고 다시 실행했다. 인터넷 지연·6인 장시간 플레이는 실행하지 않았다. 크기 제한을 위해 전체 직렬화도 한 번 수행하며, 최근 기준의 독립 사본을 유지하므로 CPU·메모리 비용이 없어지는 최적화는 아니다.


## O05 — 생물 모델 생성 프레임 분리

현재 지상 스트리밍은 비동기로 받은 PackedScene을 직접 전달하고, 근거리 모델을 먼저 생성한 뒤 원거리 모델은 다음 생성 예산에서 완성한다. 기존 프레임당 생물 생성 수를 근거리/원거리 모델이 공유한다. 대기 중에도 근거리 모델을 표시하며, 원거리 완성 시 현재 거리 선택·외형·동작을 적용한다. 같은 LOD의 표시 상태를 매 프레임 다시 쓰지 않고 공격 타이밍 JSON도 재사용한다. 도감·사건 등 기존 호출의 즉시 두 모델 생성 방식은 유지한다.

실제 Forward+에서 동물/식물 두 종류의 근거리/원거리와 이동/섭식 동작 8개를 변경 전 코드와 비교했다. 같은 모션 시각에 고정한 렌더의 3픽셀 간격 RGB 표본 오차는 모두 0이었다. 지연 생성 중 표시 유지와 완성 후 LOD 전환 6개도 통과했다. 생명이 있는 별도 T1 원정에 들어가 현장 생물 네 개의 두 모델이 완성되는 것을 확인하고 화면을 직접 검수했다. 이 실행의 근거리 생성 최대는 4.851ms, 원거리 완성 최대는 0.921ms였다.

검수 자료: `output/optimization-20260911/deferred-lods.log`의 모델 비교, `field-lods.log`의 현장 확인, `field/lod-*.png`, `living/field-lods.png`. 초기 렌더 비교 도구는 숨겨진 모델의 시간이 진행되고 있어 동일 시각 고정을 바로잡았다. 최초 지형 검사용 행성은 정상적인 무생물 행성이므로, 모델 완성 확인은 생명권이 있는 새 검사용 행성으로 옮겼다. 무생물 행성의 규칙이나 저장을 변경하지 않았다.

단일 GLB의 노드 생성 자체를 중간에 나누지는 않는다. 이 커밋은 모델·모션 품질이나 모션 갱신률을 낮추지 않는다. 별도 작업 중인 8,000종 리깅 코드의 반복 뼈 검색과 더 가벼운 전용 원거리 자산은 이번 커밋에 포함하지 않았다.
