# 항성 좌표 영속 캐시·목적지 행성 준비

## 확정 요청 — 2026-09-07

사용자는 은하 성능 설명 후 주변 좌표 캐싱과 도착할 항성계의 사전 준비, 관련 커밋을 요청했다. 행성 수·은하 시드·기존 좌표·항해 규칙은 유지한다.

## 구현

`FrontierStellarRoutes`는 한 은하의 좌표·공간 셀을 메모리에 유지한다. 처음에는 현재 항성계가 속한 반경 구역부터, 이후 인접 구역 순으로 준비한다. 항성계 ID가 반경 구역별로 배분된 현재 생성기 구조를 이용한다. 임의 시드의 실제 가까운 별을 계산 없이 알아내는 방식은 아니며 같은 구역의 다른 방향도 함께 계산한다.

- 좌표는 1,024개 단위 페이지로 `user://navigation_cache/<식별값>/`에 저장한다. 테스트는 `--crew-folder`의 별도 캐시를 사용한다.
- 은하 ID·시드·좌표 생성 버전·행성 수·항성계 배분 수·내외곽 반경·티어 구역 수로 저장 위치를 구분한다. 생성 수식이 바뀌면 캐시 버전도 올린다.
- 첫 실행은 프레임당 1.5ms 계산 예산으로 페이지를 생성한다. 완료한 페이지를 임시 파일에 기록하고 원자적 이름 변경으로 반영한다. 페이지 읽기/쓰기 한 번의 실제 파일 I/O 시간은 이 예산을 넘을 수 있다.
- 다음 실행은 페이지를 읽고 개수·자료형·체크섬·유한 좌표를 확인해 공간 셀에 넣는다. 좌표 해시 계산은 생략한다. 손상·미완성·읽기 불가 캐시는 게임 저장을 바꾸지 않고 재생성한다.
- 우선 구역 때문에 좌표가 순서대로 준비되지 않으므로 개별 준비 비트와 삽입 순서를 유지한다. 미준비 좌표의 기본값을 실제 항성계로 표시하지 않는다. 주변 결과는 좌표가 추가될 때 갱신한다.
- 메모리 캐시는 한 은하로 제한하고 은하 변경 시 비운다. 디스크는 방문 은하별로 유지하며 자동 총용량 정리는 아직 없다. 좌표 본체는 백만 행성/12만5천 항성계 기준 약 1MB이며 공간 셀·객체·파일 헤더 메모리는 별도다. 삭제해도 다시 생성할 수 있는 파생 캐시다.

`FrontierSpaceFlight`는 목적지 하나의 행성 모델만 항해 중 한 프레임에 하나씩 생성해 숨겨 둔다. 항성계 전환 시 완성된 객체를 그대로 사용하고 준비가 덜 된 행성만 기존 생성 경로로 처리한다. 목적지가 변경되면 이전 준비를 정리하고, 준비 객체는 부모 장면 종료 시 함께 해제된다. 도착 시 실제 공전 시각으로 위치를 갱신한다. 즉시 다른 메시로 교체하던 불필요한 고해상도 구 메시 생성도 제거했다.

현재 준비 범위는 행성 모델·재질·대기 객체다. 항성·위성/소행성 등 시스템 장식·정거장 생성과 GPU 셰이더 최초 컴파일까지 비동기화한 것은 아니다. 행성 지표 청크나 산업 시뮬레이션을 전 은하에 생성하지 않는다. 기존 Blender 모델·Godot 재질·ElevenLabs 항해 음향을 재사용하며 새 제작 자산은 없다.

## 확인

- `tests/check_navigation_cache.gd`: 현재 반경 구역 우선, 생성 좌표 일치, 페이지 기록/재사용, 손상 캐시 재생성, 시드/설정 분리 확인. 최종 실패 0. 첫 페이지 생성 1,024개, 재사용 복원 1,024개이며 해당 페이지 좌표 재생성 0.
- `tests/check_planet_preparation.gd`: 실제 Godot 4.7.2 Metal Forward+ 창에서 항해 중 목적지 12행성 숨김 준비, 도착 시 12객체 식별자 재사용, 준비 상태 정리·저장 확인. 실패 0. 실제 도착 화면은 로컬 `test-results/navigation-cache/arrival.png`에서 검수했다.
- 캐시 시험의 초기 페이지 경계 검사에서 다음 페이지 일부 생성까지 포함돼 실패했다. 페이지 완료 시 해당 프레임 작업을 마치도록 조정하고 같은 최소 검사를 재확인했다.

게임 전체 FPS 향상 수치·완전 무정지 진입을 주장하지 않는다. 전체 회귀·다중 클라이언트·인터넷·긴 원정은 이번 확인 범위가 아니다. 저장 원본과 다른 작업의 미커밋 변경은 보존한다.
