# 현재 원정 성능 조사 — 2026-09-09

사용자 제보: 중간 옵션에서도 **지상 이동·시점 회전과 우주 비행**의 프레임 저하가 크다. 현재 기본 원정에서 저하를 재현하고 병목 후보를 구분했다. **조사와 진단 도구 추가이며 최적화 구현 완료가 아니다.** 모델·INK 표현·게임 설정 기본값은 이번 조사에서 변경하지 않았다.

Apple M2 / 메모리 24GB / Godot 4.7.2 Metal Forward+ / 1280×800. 현재 `crew_expedition.tscn`의 혼자 원정, 시드 71491, `/tmp/performance-audit-20260909` 격리 저장을 사용했다. VSync·FPS 제한을 해제하고 균형 기본값을 적용했다. 원래 사용자 저장·개인 설정은 사용하지 않았다.

## 확인한 비용과 우선순위

### 1. 팝업 여부 확인이 전체 장면을 반복 검색한다 — 우선 수정

[`cursor_policy.gd`](../../우주-비즈니스/scripts/ui/cursor_policy.gd)의 `modal_open()`은 호출할 때마다 `tree.root.find_children("*", "Window", true, false)`로 장면 전체를 재귀 탐색한다. 지상 측정 장면에는 **6,159개 노드와 44개 Window**가 있었다. 직접 호출 중앙값은 **2.494ms**, 이를 포함하는 `feedback.blocked()`는 **2.218ms**였다. 별도 표본이므로 두 값을 더하거나 둘의 차이를 다른 비용으로 해석하지 않는다. 단순 `any_menu_open()` 중앙값은 0.011ms였다.

이 조회는 [`expedition_feedback.gd`](../../우주-비즈니스/scripts/actors/expedition_feedback.gd)의 `blocked()`를 통해 입력·물리·시각 효과·HUD에서 반복 호출된다. [`crew_expedition.gd`](../../우주-비즈니스/scripts/app/crew_expedition.gd)의 `_input()`도 마우스 이벤트 처리 전에 조회한다. 실제 한 프레임의 호출 총수는 이번에 계측하지 않았지만, 한 번에 약 2.5ms인 전체 검색을 여러 경로에서 반복하는 구조와 비용을 확인했다. 모델 부품·UI 노드가 늘수록 검사 대상도 늘어난다.

**제안:** Window 등록/해제와 표시 상태를 관리하고 등록된 팝업만 조회한다. 입력 즉시 차단·같은 프레임 팝업 열기·닫기·장면 교체·삭제를 보존한다. 팝업 검사를 제거하거나 이전 상태를 무조건 한 프레임 늦게 적용하는 방식은 피한다. 그래픽 품질을 유지하면서 줄일 수 있는 우선 대상이다.

### 2. 지형 생성이 일부 비동기여도 교체·임시 지면은 메인 스레드에 남아 있다

[`crew_surface_scene.gd`](../../우주-비즈니스/scripts/world/crew_surface_scene.gd)는 X/Z의 24m 청크 경계를 넘을 때 원경 전체 재생성을 요청한다. [`distant_terrain.gd`](../../우주-비즈니스/scripts/world/distant_terrain.gd)는 균형에서 반경 2,400m를 16m 격자로 다시 만들며, 먼 격자만 대략 18만 삼각형이다. CPU 배열 생성은 작업 스레드지만 전체 ArrayMesh 교체는 메인 스레드다. 단일 대형 메시라 지형 일부만 독립적으로 컬링하기도 어렵다.

`rebuild_fallback()`은 임시 지면의 높이·밀도·법선 검사와 메시 생성을 동기로 수행한다. 이미 지형이 준비된 지점에서도 직접 호출 중앙값이 **13.703ms**, 최대 표본이 16.133ms였다. 60fps의 전체 프레임 예산 16.67ms에 가까운 비용이다. 현재는 청크 경계와 완료 청크 변화에 따라 호출된다.

[`terrain_streamer.gd`](../../우주-비즈니스/scripts/world/terrain_streamer.gd)는 완료된 청크의 메시·삼각형 충돌체를 메인 스레드에서 설치하며, 프레임별 설치 시간 예산이 없다. 이미 준비된 상태에서도 매 프레임 `wanted` 전체를 정렬·검사한다. 정지 함수 직접 호출은 0.249ms로 팝업 검색보다 작았다.

**제안:** 원경을 고정 타일·거리 단계로 나누어 바뀐 경계만 생성하고 재사용한다. 임시 지면도 변경 타일만 갱신한다. 완료 청크 설치에 시간 예산을 두되 굴착 배치의 메시·충돌 일치와 안전한 이동 판정을 유지한다. 보행의 0.72초 끊김 전체가 특정 한 함수 때문인지는 아직 확인되지 않았다. 작업 스레드의 `max_chunk_build_ms=430.391`도 그대로 메인 스레드 정지 시간으로 읽으면 안 된다.

### 3. 우주 화면의 픽셀 처리 비용이 크다

같은 우주 장면에서 3D 배율을 100%→50%→100%로 바꾸자 평균 **25.7→55.3→21.6fps**였다. 드로콜은 약 265, 프리미티브는 약 13.7만으로 유지됐다. 화면 픽셀 처리 비용에 민감하다는 증거이며 GPU 전체 시간의 정확한 분해는 아니다.

[`sky.gdshader`](../../우주-비즈니스/assets/materials/space/sky.gdshader)는 보이는 하늘 픽셀마다 5단계 노이즈를 네 번 계산하고, 별 두 층에서 각각 주변 27칸을 검사한다. [`contour.gdshader`](../../우주-비즈니스/assets/materials/ink/contour.gdshader)는 전 화면에 깊이/법선 샘플을 반복하며, 외곽의 정방향·반대방향 샘플은 8방향 루프의 반대편 반복과 중복되는 좌표다. 단순 하늘 대체는 평균 29.9fps, 외곽선 제거는 29.7fps였으나 시간에 따른 변동이 있어 각각의 정확한 단독 개선율로 확정하지 않는다. 천체 구름·대기·가림 계산의 비용도 별도 분해가 필요하다.

**제안:** 성운·구름 저주파 성분의 저해상도 패스/캐시와 별의 선명한 최종 합성을 분리한다. 외곽선은 같은 결과를 유지하며 중복 깊이 샘플과 계산을 재사용한다. Godot의 Sky 처리 모드는 반사 큐브맵 갱신에 적용되며, 화면 하늘 셰이더 자체를 자동으로 캐시해 주지는 않는다. [공식 Sky 셰이더 문서](https://docs.godotengine.org/en/stable/tutorials/shaders/shader_reference/sky_shader.html).

### 4. 균형 설정이 최근 효과의 세부 비용까지 제어하지 않는다

현재 원정은 [`client_settings.gd`](../../우주-비즈니스/scripts/ui/client_settings.gd)를 사용한다. 과거 `graphics.json`/`FrontierGraphics`의 균형 90m 그림자와 달리 현재는 **180m**다. 따라서 과거 1.2의 약 60fps 기록은 현재 균형의 성능 근거가 아니다.

현재 프리셋은 배율·MSAA·후처리·그림자·원경을 조절한다. 하지만 하늘 노이즈 반복 수, 지질 장식 생성 범위/후보 수, 새 대기·구름 연산은 별도 품질 예산으로 연결되지 않았다. 지질 장식과 복셀 지형의 활성 범위는 그래픽 시야거리와도 별개다. 사용자 정의 지형 메시에는 생성된 LOD가 없어 뷰포트 LOD 숫자만 바꿔도 지형이 자동으로 단순해지는 것은 아니다.

지상 그림자를 끄면 약 **1,754→563 드로콜**, 원경을 숨기면 약 **185만→76만 프리미티브**로 줄었다. 다만 그 구간 FPS는 뚜렷하게 좋아지지 않았다. 이 측정에서는 CPU와 기타 처리 비용을 먼저 해소해야 하며, 그림자만 낮추면 해결된다고 보지 않는다. 렌더 프리미티브에는 그림자·추가 패스가 포함된다. [Godot의 컬링·LOD·인스턴싱 설명](https://docs.godotengine.org/en/stable/tutorials/performance/optimizing_3d_performance.html).

### 5. 현재 게임을 대표하는 성능 측정 경로가 필요하다

기존 `benchmark.gd`, `benchmark_surface.gd`, `benchmark_space.gd`는 과거 캠페인 또는 별도 탐험 장면을 사용한다. 현재 원정의 선박 장치·지표 장식·협동 세션·최근 효과 전체를 대표하지 않는다. 이번에 [`benchmark_crew_current.gd`](../../우주-비즈니스/tests/benchmark_crew_current.gd)를 추가했다. 새로운 전체 테스트 묶음이 아니라 제보된 성능 문제를 재현하고 분리하기 위한 도구다.

현재 이미 적용된 최적화도 있다. 지상에서는 뒤쪽 우주 SubViewport 렌더가 중단됨을 실제 상태 `UPDATE_DISABLED=0`으로 확인했고, 장비 미리보기는 숨기면 중단하는 코드가 있다. 지질 장식에는 MultiMesh, 생물에는 거리별 모델, 지형에는 작업 스레드 생성이 적용되어 있다. 최적화가 전혀 없는 상태는 아니지만 남은 공통 CPU 비용과 이동 중 갱신이 크다.

- GPU 타이머가 0을 반환해 `null`로 기록했다. JSON의 process/physics 모니터는 갱신 주기가 있는 표본이며 한 프레임의 독점 CPU 시간으로 더하거나 비율을 계산하지 않는다. 프레임 간격과 직접 함수 호출 시간이 주 근거다.
- 게임 시뮬레이션·낮밤·생물은 계속 진행되므로 구간별 가시 물체·그림자와 드로콜이 변했다. 완전히 고정된 A/B 벤치마크가 아니며 효과별 작은 FPS 차이를 확정 성능 이득으로 쓰지 않는다.
- 첫 통합 진단 중 기기 반응이 크게 느려져 자체 진단 프로세스를 종료했다. 당시 별도 Godot 프로세스도 관찰되어 해당 착륙 구간 성능은 제외했다. 지상/CPU를 별도 재실행했고, 우주는 환영 편지를 닫은 화면으로 다시 측정했다. 최초 진단 스크립트의 타입 추론 오류는 수정 후 실행했다.
- 조사 시점에 다른 지표 표현 작업의 미커밋 변경이 존재했다. 해당 변경은 보존하고 현재 작업 트리에서 조사했다. 이번 조사에서 제품 코드나 모델을 최적화한 것은 아니다.
- Windows·사용자의 실제 기기/해상도·6인·대규모 자동화·성간 비행/실제 마우스 연속 회전은 미측정이다. 우주 정지 화면도 느리다는 점과 지상 보행 끊김을 확인했다. 기존 전체 회귀는 실행하지 않았다.
