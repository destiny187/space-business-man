# 원경 타일·충돌 준비·지형 계산 최적화

2026-09-09 사용자 승인: [1차 최적화](78-performance-and-simple-settings.md) 이후 남은 원경 전체 교체, 충돌체 생성, 반복 지형 계산을 개선한다. 상황에 따라 커밋을 나누며 기존 지형 모양과 굴착/충돌 규칙을 유지한다.

## 현재 변경

원경은 월드에 고정한 **512m 타일**로 나눈다. 기존 16m/32m 표면 격자는 유지한다. 이동하면 근거리 전환부에 겹치는 타일과 새 시야에 들어오는 타일만 작성한다. 높이와 법선 표본도 재사용한다. 시야 경계는 타일 끝으로 확장되며, 카메라 표시 거리와 플레이 가능한 충돌 범위는 기존 규칙을 따른다. 보통 범위의 원경 갱신 검사에서는 100개 타일 중 4개를 교체했다.

CPU 배열은 기존 작업 스레드에서 만들고 GPU 업로드는 메인 스레드의 2ms 예산으로 나눈다. 이전 지면을 유지하다가 새 근거리 전환 링과 해당 타일의 구멍을 함께 교체한다. 오래된 타일·업로드한 CPU 배열을 해제하고, 연속 이동/품질 변경은 마지막 요청을 이어 처리한다. 루트 메시가 이제 근거리 전환 링이므로 전체 범위는 `terrain_bounds()`로 조회한다. 타일별 화면 밖 제외가 가능해지는 대신 메시별 제출 횟수는 늘어날 수 있다.

근접 청크는 **시각 메시 준비 → 충돌체 준비 → 함께 설치**로 나누었다. 작업 스레드에서 원본 정점/인덱스로 충돌 삼각형을 미리 작성한다. GPU에 올린 ArrayMesh를 다시 읽어 TriangleMesh/BVH를 구성하던 경로를 제거했다. 기존 Godot 충돌 생성과 같은 0.0001m 정점 맞춤을 적용하고 실제 출력 배열 일치를 확인했다. [Godot TriangleMesh 구현](https://github.com/godotengine/godot/blob/master/core/math/triangle_mesh.cpp)의 맞춤 처리를 참고했다.

실제 SceneTree 연결과 물리 엔진의 최종 설치는 메인 스레드에 유지한다. 공유 노드/렌더 자원을 작업 스레드에서 수정하지 않는다. [Godot 스레드 사용 기준](https://docs.godotengine.org/en/stable/tutorials/performance/thread_safe_apis.html). Jolt 내부 형상의 모든 생성을 별도 스레드로 옮긴 구현은 아니다. 굴착은 모든 관련 메시/충돌 준비가 완료될 때까지 이전 충돌을 유지한 뒤 한 번에 교체한다.

한 청크의 13×13×13 밀도 검사에서 **같은 x/z 열의 높이를 13번 계산하던 것을 1번으로 줄였다.** 2,197회의 높이 조회가 169회가 된다. 동굴·굴착·기반암 밀도 판정은 기존대로 각 3D 좌표에서 수행한다. 정점 법선의 위/아래 표본과 색상 계산도 같은 중심 높이를 공유한다. 새 영구 캐시나 저장 형식 변경 없이 작업별 배열로 재사용한다.

## CPU 비교와 실제 원정

기준 커밋은 `95ad7efe`이며 현재 구현과 같은 프로세스·시드/지형 조건에서 원본 배열과 처리 시간을 비교했다. Apple M2, Godot 4.7.2 Metal Forward+다. 아래 CPU 수치는 각 대표 작업 1회의 직접 경과 시간으로, 게임 전체 FPS나 모든 지형의 보장값이 아니다.

| 작업 | 이전 | 변경 후 |
| --- | ---: | ---: |
| 표본이 캐시된 2,400m 원경, 24m 이동 | 115.69ms | 27.97ms |
| 대표 지표 청크 생성 | 51.17ms | 35.92ms |
| 대표 지하 청크 생성 | 43.06ms | 29.45ms |

독립 검사에서 개별 원경 타일 업로드 최대 0.68ms, 근거리 시각 준비 최대 0.12ms, 충돌 준비 최대 0.084ms, 청크 설치 최대 1.74ms였다. [CPU 비교 원본](media/terrain-streaming-optimization/cpu-comparison.json).

현재 원정의 별도 실제 창에서는 시드 71491·1280×800·보통·렌더 100%·VSync/FPS 제한 해제로 새 원정→착륙→110.12m 보행을 확인했다. 지상 정지는 **36.7 FPS**, 보행 평균은 **32.8 FPS**(30.51ms), 보행 p95는 53.30ms, 최대는 244.77ms였다. 1차 측정의 지상 34.5/보행 29.2 FPS·최대 374.75ms는 이전 상태의 참고값이다. 다른 지표 효과 작업·세계 시간·OS 부하도 달라 **두 실행의 차이를 이번 변경만의 개선율로 해석하지 않는다.** 우주 59.4 FPS도 측정됐지만 이번 지형 변경의 효과로 주장하지 않는다. [현재 원정 원본](media/terrain-streaming-optimization/current-expedition.json).

**잔여 비용:** 위 독립 검사와 달리 실제 원정 전체 수명(초기 로딩 포함)에는 근거리 메시 업로드 최대 22.48ms, 스트리머 한 프레임 최대 30.94ms, 원경 메인 처리 최대 31.57ms가 관측됐다. 2/3ms 예산은 작업 사이에만 확인하므로 단일 GPU 호출·최종 설치를 중단하는 강제 상한이 아니다. 보행 최대 244.77ms를 특정 함수 하나의 CPU 비용으로 확정하지 않는다. 안정적인 지상 60 FPS는 아직 달성하지 않았다.

## 검증 범위

- `tools/test_terrain_optimization.sh`: 기준 커밋의 구현을 `/tmp`에 추출해 지표/지하 메시·법선·색·굴착 결과, 기존 충돌 삼각형의 정확한 일치, 원경 삼각형 보존·근거리 링 일치, 타일 재사용, 음수 좌표·연속 이동/품질 변경·거리 축소, 실제 물리 레이와 굴착의 일괄 충돌 교체 **18개 통과**.
- `test_terrain.gd`: 관련 지형/저장 규칙 20개 통과.
- `benchmark_crew_current.gd --verify-optimization`: 현재 원정 착륙/보행·시점 입력·설정 중 차단·장비 표시 복귀·로컬 진단 굴착 완료 **11개 통과**, 최종 실행의 스크립트/엔진 오류 없음.
- 실제 Forward+ 지상 정지/보행 화면에서 지면·산 윤곽선·장비 모델을 확인했다. 테스트 중 완료한 작업 ID 재조회 오류와 기존 충돌 정점 맞춤 차이를 발견해 수정했다.
- 실제 채집 거래·건설/로봇 전체 동선, Windows·6인·장시간 여행은 이번 확인 범위가 아니다. 기존 사용자 저장/설정은 사용하지 않고 `/tmp`의 격리된 원정만 사용했다.
