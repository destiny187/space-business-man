# 선체별 실내와 게스트 비행 관전

## 2026-09-13 사용자 요청

선체마다 더 풍부한 실내 형태와 장식을 적용하고, 정면 외에 측면과 위쪽으로도 넓게 바깥을 볼 수 있게 한다. 호스트가 아닌 승무원은 특정 키로 호스트를 기준으로 자유롭게 둘러보되 조종하지 않는 관전을 사용한다. [168의 내부 조사](168-advanced-hulls-and-skills.md#2026-09-13-후속--선체-내부-조사)에 대한 후속 구현이다.

## 구현 범위

- 공동 원정선 9종에 Blender 전용 실내를 배정한다. 기존 단일 실내 GLB를 덮어쓰지 않는다.
- KESTREL / ASTER / ORION: 곡선 압력 아치·짐벌 관측 장비·분석 좌석과 상부 관측 링. SWIFT / PEREGRINE / SPECTRE: 대각 캐노피·가속용 버킷 좌석·벡터 계기·위상 코어. MULE / OX / ATLAS: 좌석 보호 프레임·고정 화물함·상부 갠트리.
- 각 실내는 정면, 좌우 다섯 구획씩, 천창 다섯 구획으로 총 16개 개구부를 사용한다. 창밖 카메라는 선내 눈 위치·회전·FOV를 선박 좌표계로 변환하고 모든 개구부가 화면의 같은 광선을 표시한다. 정면 화면을 측면에 반복하는 방식이 아니다.
- F8은 게스트 관전 진입/복귀, Esc는 복귀, 마우스는 360도 둘러보기, 휠은 거리 조절이다. P 승무원 메뉴와 첫 승무원 가이드에도 안내한다. 호스트의 현재 우주선이 기준이며 호스트가 FINCH로 독립 비행 중이면 해당 FINCH를 따른다. 지상 호스트 관전은 이번 범위가 아니다.
- 관전 중 개인 이동·스캔·발사·스킬·조종 입력은 차단한다. 조종 권한을 위임받은 게스트도 관전에서는 조종할 수 없다. 일반 메뉴의 안전 제동 입력도 보내지 않아 관전 키가 브레이크를 누르지 않으며, 속도·자동 항해는 기존 시뮬레이션이 이어간다. 키/마우스를 놓기 전 복귀 직후의 입력 재개도 막는다. 세계는 계속 진행하며 캐릭터 위치·장비·권한을 변경하지 않는다.
- 호스트 착륙, 관전 정보 소실, 연결 종료, 자신의 착륙 연출 시작 시 원래 시점으로 돌아온다.

## 기존 저장과 행동 범위

실내 ID는 운용 선체에서 읽는다. 6인 생성 위치·공동 보관함·증강/연구대와 기본 8×16m 보행 영역을 유지하므로 저장된 승무원을 재배치하지 않는다. 외장 성능·화물·스킬도 바꾸지 않는다. FINCH의 전용 보행 실내와 별도 방/문 개폐는 추가하지 않았다.

선체가 바뀐 경우에만 장식 메시와 조명을 갱신한다. 배우·물리 바닥/벽·장치 노드를 유지한다. 같은 선체의 반복 스냅샷은 실내를 재생성하지 않는다. 교체할 때 이전 재질 캐시를 비워 선체를 오가도 계속 누적되지 않는다. 호스트가 다른 장소에 있어도 원격 공동 선내에는 같은 충돌 정의를 생성한다.

관전은 로컬 표시 상태다. 별도 저장 거래나 관전 RPC를 만들지 않으며, 정기 스냅샷 fanout 한 번에 작은 host_view(호스트/기체 구분·항해 상태)만 만든다. 원래 은하·생태·지형을 복사하지 않는다. 기존 정기 스냅샷의 전체 직렬화 비용은 남는다. 관전 카메라는 처음 사용할 때 생성하고 숨겨진 동안 갱신하지 않는다. 관전 중 가려진 개인 우주 렌더와 주 3D 패스를 끈다. 각 창마다 월드/카메라를 생성하지 않는다.

## 제작과 확인

제작기: `tools/build_vessel_interiors.py`, 원본/매니페스트: `art/blender/crew/interiors/`, 게임 자산: `assets/models/crew/interiors/`. 공통 INK 재질·베벨·정적 메시 병합을 적용하고 Blender EEVEE로 9종을 렌더했다. 최종 실내는 47,848~69,000 삼각형이며 현재 선체 하나만 렌더한다. 실제 게임 확인 결과는 아래에 추가한다.

기존 ElevenLabs 선박 내부/외부 소리와 전환 확인음을 재사용한다. 새 음원 생성은 없다. [재사용 정보](../../audio/manifests/vessel-interiors-reuse.json)에 원본 경로·해시·용도를 남긴다.

Metal Forward+ / Apple M2의 현재 원정 장면과 독립 SceneMultiplayer 두 개의 실제 로컬 ENet 연결로 확인한다. 검사 명령은 `./tools/godot.sh --script res://tests/check_vessel_interiors_play.gd -- --crew-ui-test --crew-folder=/tmp/space-vessel-interiors`다. 사용자 원정 파일은 사용하지 않는다.

첫 실행에서 창 화면을 색 변환 없이 재사용하여 별 배경이 밝아지는 현상을 발견했고, `source_color`로 sRGB를 복원했다. 최종 모델은 좌석/아치/화물 구조의 차이를 더 강조하고, 걸어서 점프하는 높이(기본 약 2.86m) 위로 벽 부착 장비를 올려 보행 공간을 유지했다. 실제 정면·좌측·천창·후방과 960×640 관전을 캡처한다.

최종 **43개 확인, 실패 0**. 실제 ENet 게스트가 받은 9개 선체의 모델 교체, 창 방향/FOV, 배우·장치·충돌 노드/저장 위치 보존, 재질 캐시 한도와 갠트리 움직임, F8·Esc 복귀, 360도 시점, 조종사인 게스트의 사격/제동/이동 차단, 기존 확인음 호출, 960×640 안내, 연결 종료·저장 복원을 확인했다. FINCH 기준과 지상 비행 정보 제외는 좁은 상태 구성 검사이며 FINCH 전 과정을 직접 비행한 결과는 아니다. 원본/GLB/WindowPanes/렌더 목록 9개 연결도 확인했다.

커밋 대상으로 분리한 코드의 파싱 검사에서 앞선 `40b6ae2b6`의 `incident_view.gd`가 참조하는 `FrontierTargetHealth` 파일 누락을 발견했다. 기존 공용 표시 파일과 UID를 함께 추적하여 해당 의존성을 복구했다.

관전 입력 검사는 게임의 키 처리 함수와 실제 게스트 movement RPC를 사용했다. 물리 키보드/마우스 직접 조작·외부망·6인·최종 청감·장시간 성능은 미확인이다. 작업 중 한 번 초기 진입 90초 시간 초과, 한 번 종료 시 ObjectDB 1개 경고가 있었고 마지막 실행에서는 재현하지 않았다. 원인을 특정한 것으로 기록하지 않는다. 원시 로그는 `output/vessel-interiors-final-play.log`, 전 대상 캡처는 `output/vessel-interiors/`에 둔다.
